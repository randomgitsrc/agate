## BLOCKING 1：check-tdd-red.sh 对 vitest 的 B/A 类判定，用真实 vitest 测出来是错的

计划里我已经验证过"默认 `ERROR_PATTERN` 匹配不到 vitest 输出，需要 `TEST_ERROR_PATTERN="Failed Suites [0-9]+"` 覆盖"，这次实现也确实按这个思路加了脚本头部注释和 bats 测试（TDD.N2/N3/N4）。**但我这次用真实 vitest 装了一遍，端到端跑一次官方推荐配置，发现 B 类场景被误判成了 A 类：**

```bash
$ cd /tmp/vitest-test  # 真实 npm install vitest 的沙箱
$ cat src/foo.test.ts   # import 一个项目内、尚未实现的模块（合法的 B 类红灯）
import { bar } from '../src/bar'
...

$ TEST_RUNNER="npx vitest run" TEST_RUNNER_FLAGS="--reporter=default" \
  TEST_ERROR_PATTERN="Failed Suites [0-9]+" PROJECT_MODULE="src/bar" \
  bash check-tdd-red.sh
TDD_CHECK: A-class error (test code has bugs, fix before proceeding)
SCRIPT EXIT: 1        # 应该是 exit 0（B 类，合法红灯），实际拦截了
```

**根因**：脚本里判定 B 类还是 A 类靠的是下面这行二级正则（这次改动没碰它）：
```bash
IMPORT_ERRORS=$(echo "$RESULT" | grep -E '(ImportError|ModuleNotFoundError|Cannot find module|ClassNotFoundException|NoClassDefFoundError|unresolved import):' || true)
```
要求关键词后面**紧跟一个冒号**。但真实 vitest 的报错原文是：
```
Error: Cannot find module '../src/bar' imported from /tmp/vitest-test/src/foo.test.ts
```
冒号跟在 "Error" 后面，不是跟在 "Cannot find module" 后面——这条正则**永远匹配不到**真实 vitest 的 import 错误行。`IMPORT_ERRORS` 恒为空，脚本直接跳过整个 A/B 判定分支，落到最后的兜底逻辑：
```bash
# A 类：测试代码自身有 bug
echo "TDD_CHECK: A-class error..."
exit 1
```
**结果是：对 vitest 项目，任何 collection error（不管是合法的 B 类，还是真的 A 类）都会被兜底判成 A 类、exit 1。** 这比修复前（`-q` 直接崩溃）更隐蔽——崩溃至少明显报错会被立刻发现，这个是"脚本正常跑完、给出一个看起来合理但实际错误的判断"，会让 vitest 项目的 implementer 以为自己测试代码写错了，反复检查一个根本没问题的 import 语句。

**为什么 bats 测试没抓到**：TDD.N3/N4 用的合成 fixture 文本是"`ImportError: cannot import name 'Yyy' from 'myapp.foo'`"这种 pytest 风格的措辞（关键词后面手动加了冒号），不是真实 vitest 会输出的文本格式，测试断言的是"我编的这段话能不能被正则认出来"，而不是"vitest 真实会说的那句话能不能被正则认出来"——测试自证成立，但没验证到关键假设。

**建议修复**：仿照现有 `FAIL_PATTERN`/`ERROR_PATTERN` 的设计，把 `IMPORT_ERRORS` 那条正则也做成可配置（如新增 `TEST_IMPORT_ERROR_PATTERN` 环境变量，默认值保持现状不破坏 pytest 向后兼容），vitest 场景下额外设置为能匹配 `Cannot find (module|package) '` 这类真实格式的正则。改完后必须用真实 vitest（不是合成 fixture）重新跑一遍我上面这个复现步骤确认 exit 0。

## BLOCKING 2：agate-render-dispatch-prompt.sh 渲染结果里，subagent 拿到自己角色定义文件的路径是断的

`dispatch-prompt.md` 模板里最开头几行：
```
## 你的角色定义
读取并严格遵循：
{agate_root}/assets/{execution-roles|review-roles}/{role}.md
```
`{agate_root}` 和 `{execution-roles|review-roles}` 这两个占位符**脚本从来没替换过**——即使脚本自己在最上面就已经算出了 `AGATE_ROOT` 变量。实测：

```bash
$ bash agate-render-dispatch-prompt.sh P4 implementer /tmp/rendertest
...
{agate_root}/assets/{execution-roles|review-roles}/implementer.md
```
这行字面意思原样保留在渲染产物里。如果主 Agent 真的把这段渲染结果原样复制去派发 subagent，subagent 第一步"读取角色定义文件"就会去读一个字面上写着花括号的、根本不存在的路径——整个派发从第一步就断了。

这个问题上一轮"独立实施评审"（bcfa0b3 那次）修过 `P{N}`、`{role}` 两个占位符替换缺失，但**没有把同一类问题的另外两个实例（`{agate_root}`、`{execution-roles|review-roles}`）一起排查干净**，说明那一轮的检查方式是"针对已发现的具体报错逐个补丁"，没有做一次"模板里所有 `{...}` 占位符逐个核对是否都有对应替换规则"的系统性扫描。

**同一批漏检的还有**（严重性较低，一并列出）：
- `{上一阶段文件名}`（Header 的 `parent:` 字段）——`dispatch-prompt.md` 自己的"关键提醒"明确写了"主 Agent 必须确保 phase/task_id/parent/trace_id 四个字段已直接填好"，但脚本没有对应的替换规则，这个字段会原样保留占位符。这个不像 `{agate_root}` 那样有现成变量可以直接填（"上一阶段文件名"依赖任务具体产出，脚本目前的三个入参 PHASE/ROLE/TASK_DIR 推不出来），可能需要新增一个入参，或者明确注释"此字段需要主 Agent 复制渲染结果后手动填写"，但目前脚本注释和文档都没提这个限制，容易被当成"已经全自动填好"。

**建议修复**：
1. `{agate_root}` 直接用脚本已有的 `$AGATE_ROOT` 变量替换——这个是纯粹的遗漏，修起来就一行 sed
2. `{execution-roles|review-roles}` 需要判断 ROLE 属于哪一类（可以用文件是否存在于 `$AGATE_ROOT/assets/execution-roles/${ROLE}.md` 还是 `review-roles/${ROLE}.md` 来判定，判断不出来就报错退出，而不是留一个二选一占位符在输出里）
3. `{上一阶段文件名}` 至少要在脚本输出或注释里明确提示"这个字段渲染脚本填不了，主 Agent 复制后必须手动补上"，不能让人误以为渲染产物是可以直接照抄不看的成品
4. 新增一条兜底断言型测试：渲染结果里不应该残留任何 `{xxx}` 形式的占位符（除了确认是"故意留给主 Agent/subagent 自行处理"的字段，这些字段要在脚本注释里明确列出白名单）——现有 RP.4 的断言只针对"上一轮明确报出来的几个坏点"逐个 `!= *"{role}"*` 这样点名检查，没有一条通用兜底，导致这次的 `{agate_root}` 漏网
