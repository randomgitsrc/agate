# agate 主动架构演进机制：方案设计与评估

> 本文回应主主题的**主动部分**：agate 如何主动让架构变好，而非被动等债爆雷。
> 技术债闭环（被动部分）已另文立项，本文不重复。
>
> 本文是方案选型文档，不是实施计划。选定后仍需走完整 P0-P8。

## 0. 先讲清楚现实约束（本节初稿写错了，已重做）

**agate 有约 23 个历史工作项，不是 1 个。**初稿据一份不完整的看板断言"只有 1 个已完成任务"，并据此否决了两个方案——那个前提是错的，本节是重做后的结果。

| 事实 | 数据 | 说明 |
|---|---|---|
| commit 中出现过的任务编号 | **24 个**（T001…T091） | 其中 T001 与 T091 是**同一个任务**（中途改名，见 T001 复盘），故实为约 23 个 |
| 有完整 P0-P8 归档产出的任务 | **1**（T001） | `docs/archived/tasks/` |
| `active-tasks.md` 已完成表中的任务 | **1**（T001） | 看板只覆盖当前编号纪元，早期任务未回填 |
| 走 `wf(` 前缀的 commit | 32 / 661（4.8%） | 早期任务多用 plan+review 轻流程，非完整 P0-P8 |
| `refactor:` commit | **20**（其中 19 个不引用任何任务编号） | 重构确实在发生，且基本在任务流程之外 |

**每任务波及文件数是可以算出来的**（按 commit message 中的任务编号归集），24 个数据点实测节选：

```
2026-06-21  T016   files=34      2026-07-13  T053   files=1
2026-06-23  T019   files=90      2026-07-24  T068   files=47
2026-06-26  T022   files=13      2026-08-03  T085   files=15
2026-06-29  T027   files=14      2026-08-06  T080   files=28
2026-07-01  T045   files=16      2026-08-09  T090   files=14
2026-07-11  T052   files=2       2026-08-09  T091   files=19
```

**但这组数据无法解读——这才是真正的约束，且比初稿写的"没有数据"更根本：**

1. **没有基线**。T019 波及 90 个文件，是架构不好还是任务本来就大？**无从判断。**没有"这个改动本该波及多少"的参照，绝对值不含信息
2. **趋势不成立**。按时间排序看不出单调方向（早期 T019=90，后期 T090=14），但这只反映任务大小不同，不反映架构变化
3. **归集方法粗糙**。按任务编号 grep commit message，会把顺带提及该编号的文档 commit 也算进去；且 T001/T091 改名造成重复计数

**推论（与初稿相反）**：否决"数据驱动的周期审视"（方案丁）的理由**不是没有数据**，而是**有数据也读不懂**。而这恰好指向出路——缺的那个基线，只能由**事先做出的预测**提供。这正是方案丙存在的理由，见 §2。

另外两条结论保持不变，且现在有更强的证据：

- **重构已经在发生（20 次，19 次不挂任务编号）**。"重构一等任务"不是引入新行为，是把既有行为纳入轨道，落地风险低
- **agate 自身开发大部分不走完整 P0-P8**（4.8% 用 `wf(` 前缀，仅 1 个任务有完整归档）。所以任何依赖完整任务产出的机制，**agate 自己只有 1 个样本可验**，真正的试验场是下游项目

## 1. 先明确目标形态（回答"agate 该长成什么样"）

### 1.1 一个必须先放弃的目标

**agate 不可能保证架构优秀。**理由不是能力不足，是结构性的：

- 代码正确性有 ground truth（测试红绿），所以 gate 可以判定
- **架构好坏没有 ground truth**。任何"架构评审 subagent 说架构没问题"的输出，都无法被独立检验
- 这正是 LIMITATIONS 局限 3 最严重的形态：不是"agent 可能钻空子"，而是**这个 bar 根本不存在客观形态**，agent 说什么都不算错

上一轮评审还实测过一个相关结论：连**机器指标**都不可靠——churn×LOC 热点把 agate 近期最产缺陷的文件排在第 96 名（详见 `review-lifecycle-discussion-response-20260812.md` §4.2）。

所以主动机制既不能靠 agent 的架构判断，也不能靠现成的结构指标。**任何绕过这两条的方案都是自欺。**

### 1.2 可以达成的目标形态

把目标从"保证架构优秀"降级为四条**可验证**的能力：

| 目标 | 可验证形态 |
|---|---|
| 架构意图显式化 | 设计决策与约束被写下来，而非隐含在代码里 |
| **变更成本可见且可比较** | 每次改动的实际波及范围有记录，可与预期对照 |
| 重构有合法路径 | 重构能立项、有验收口径，不必伪装成功能任务 |
| 架构问题无法被静默拖延 | 客观失败事件**强制**触发重新考虑（不强制改，强制记录决定） |

**"让架构问题无法被静默地拖下去"，而不是"保证架构优秀"。**这是本文认为 agate 能诚实承诺的上限。

### 1.3 贯穿全文的设计原则

上一轮从技术债得到的原则在这里同样适用，且更重要：

> **把强制动作挂在客观事件上，不挂在判断上。**

`retreat` 发生 → 必须建债务条目（客观事件，逻辑上不可能误报）。本文要找的，是架构领域里同类的客观事件。

## 2. 核心思路：把不可验证的判断，变成会被现实检验的预测

既然"架构好不好"不可验证，就不要问这个问题。改问一个**会被后续现实结算**的问题：

> **"如果将来要做 X，需要改动哪些地方、大概多少处？"**

这句话在 P2 设计时是**预测**，在后续任务真的做 X 时变成**可对照的事实**。

为什么这个转换是关键：

- **agent 无法靠断言过关**。说"架构良好"没有代价；说"加 X 只需改 2 处"会在半年后被现实打脸
- **它提供了那个缺失的基线**。§0 实测表明，每任务波及文件数算得出来但读不懂——90 个文件到底是架构烂还是任务大，没有参照就无法判断。**事先的预测就是那个参照**：不是拿绝对值去比阈值，而是拿"实际 vs 你自己当初的预测"去比。这把一个无意义的绝对数，变成了有意义的偏差量
- **它直接命中复杂度的操作定义**。<cite index="44-1">Ousterhout 把复杂度的第一个症状定义为变更放大：看似简单的改动却要求在许多不同地方修改代码；好设计的目标之一就是减少每个设计决策所波及的代码量</cite>
- **它能暴露最难发现的那类问题**。<cite index="44-1">在复杂度的三种表现里，未知的未知是最糟的——你不知道自己需要知道什么，往往要等改动之后 bug 冒出来才发现</cite>。预测失准正是"你对自己系统的理解是错的"这件事**第一次可被观测**的时刻。

这个转换也符合外部实践对适应度函数的定位——《Building Evolutionary Architectures》第二版专门有一节讲它应当作**检查清单而非棍棒**（"Fitness Functions as a Checklist, Not a Stick"），<cite index="3-1">其作用是说清"更好"意味着什么并帮助衡量目标是否达成</cite>，而非充当审判。

## 3. 候选方案

六个方案，其中三个是主动机制的实体，两个是使能器/补充，一个作为基线对照。

### 方案甲：纯方法论 nudge（基线对照）

只改 `architect` / `plan-eng-review` 角色卡，加入可扩展性六问（"未来加 X 要动多少？""这个边界为什么划在这里？"）。零脚本、零 gate、零字段。

- **成本**：接近 0
- **风险**：接近 0
- **问题**：完全依赖自觉。agate 整个 hardening-roadmap 的前提就是"依赖 agent 自觉的环节都是脆弱的"。作为**唯一**机制不成立，作为**附加**项免费。

### 方案乙：架构约束可执行化（复用 `gate_commands`）

**已有机制直接可用，这是本方案最大的优点。**`P2-design.md` 已经声明 `gate_commands.P5`，P5 由 verifier 执行。`phase-cards/P5-verification.md:45` 明确写着这套设计"技术栈无关"，formatter 为可选项、不提供时退化为 exit-code-only；同文件第 65 行进一步说明缺失时"优雅降级为 WARNING-only 行为，不因此新增拦截"。

新增一个同构的 `gate_commands.P5_arch`：项目自己声明架构约束检查命令，agate 只负责**要求它存在并执行它**，不关心它怎么实现。

```yaml
gate_commands:
  P5_arch:
    - "scripts/check-layering.sh"        # 项目自己写：禁止 domain 层 import infra 层
    - "madge --circular src/"            # 或直接用生态现成工具
```

- **平台中立性完美保持**：agate 不实现任何语言相关的检查，只提供挂载点。这与 `P5_formatter` 的既有设计完全同构
- **是硬检查、无判断空间**：约束要么满足要么不满足，agent 钻不了空子
- **覆盖面有限**：只能检查**你已经知道要检查什么**的约束（依赖方向、分层、循环依赖）。对"还不知道哪里会烂"完全无能为力
- **成本**：项目要自己写检查。对没有现成工具的技术栈是真实负担

### 方案丙：变更预算预登记 + 事后核对（§2 思路的实体）

P2 设计时，architect 登记 2-3 个**预期变更点**及预估波及范围：

```yaml
change_budget:
  - change: "新增一种 formatter（如 jest）"
    predicted_files: 2
    predicted_modules: ["assets/formatters"]
    basis: "formatter 是插件式挂载，新增只需加脚本 + 注册"
  - change: "新增一个 P 阶段"
    predicted_files: 8
    predicted_modules: ["phase-cards", "scripts", "rules", "tests"]
    basis: "阶段是横切概念，state-machine/gate/卡片/测试都要动"
```

后续任务在 P1 判定"本任务是否命中已登记的预期变更点"（一个勾选，成本极低）。命中则在 P6 对照：**预测 vs 实际改动范围**。偏差超阈值（如 2 倍）→ 触发一次架构复看，**强制记录结论，不强制重构**。

- **把判断变成可证伪的预测**，agent 无法靠断言过关
- **反 Goodhart 性质很好**：往大了预测（"加个 formatter 要改 20 个文件"）以求不失准，等于**主动承认架构差**，且会在 P2 评审被质疑。**把指标往好看了做的唯一方式，就是真的把架构做好** —— 这个性质很罕见，值得单独指出
- **从第 1 个任务就能开始积累**，且它提供的正是方案丁缺的那个解读基线（§0）
- **反馈周期长**：预测在任务 N 登记，可能到任务 N+k 才结算，也可能永远不结算
- **有一个真实的钻空子面**：agent 可以只登记"一定不会被触发"的琐碎变更点。缓解手段是要求变更点来自 P1 的 out-of-scope / roadmap 而非自由发挥，但**这只是部分缓解，不是封死**（见 §6.2 诚实标注）
- **每任务负担**：这是它最实在的代价，见 §5.2 的适用范围限制

### 方案丁：模块变更集中度监测（数据驱动的周期审视）

从 git + 任务编号算：每个任务触及的文件/模块数、同一模块被连续 N 个任务触及的频率。里程碑时产出数据包。

- **无需人工判断即可产出**，且 §0 已实测**数据确实算得出来**（24 个任务的波及文件数）
- **但算出来读不懂**：没有"这个改动本该波及多少"的基线，90 个文件是架构烂还是任务大无从判断；按时间排序也看不出趋势方向。这是它的根本问题，不是数据量问题
- 另有归集精度问题：按任务编号 grep commit message 会误收顺带提及的文档 commit
- 上一轮还实测过同类结构信号会漏掉真问题（churn×LOC 把最产缺陷的文件排在第 96 名）
- **判定：推迟，但保留**。一旦方案丙运行起来、积累了"预测 vs 实际"的配对数据，丁的原始数据就有了解读基线，届时可作为丙的补充视图重估

### 方案戊：独立架构审视 subagent 周期派发

里程碑时派发 `architecture-reviewer`，产出架构演进建议。

- **覆盖面最宽**，最像传统架构治理
- **但它是 §1.1 那个结构性问题的最纯粹形态**：输出是"我认为架构还行/有问题"，**没有任何独立检验手段**。producer=judge，且这次连 ground truth 都不存在
- 还要加派发负担（讨论稿第 3.4 节明确要避免）
- **判定：不推荐**。除非改造成"只产出可证伪断言"（那就退化成方案丙）

### 方案己：重构一等任务（使能器，非独立机制）

`P1-requirements.md` 加 `change_type: refactor`；P6 验收口径改为**行为不变 + 全量回归全绿 + 关键路径验收**，不伪造功能 BDD。

- **不是主动机制本身，是让前面所有机制的产出有地方去**。没有它，架构审视发现问题也无法立项，只能"以后再说"
- **风险极低**：§0 已证实重构在 agate 已发生 20 次（其中 19 次不挂任务编号），只是走在协议外。这是把既有行为纳入轨道，不是引入新行为
- **不需要新阶段、不需要新模板体系**：P0-P8 骨架完全相同，差异只在 P6 口径

## 4. 方案评估

| 维度 | 甲 nudge | 乙 约束可执行 | 丙 变更预算 | 丁 集中度 | 戊 审视 subagent | 己 重构任务 |
|---|---|---|---|---|---|---|
| 依赖不可验证判断？ | **是** | 否 | 否（预测由现实结算） | 否 | **是（最严重）** | 否 |
| 需跨任务积累才有效？ | 否 | 否 | 否（第1个任务即可登记） | **数据够，但缺解读基线** | 否 | 否 |
| 每任务负担 | 无 | 无（一次性写检查） | **有（登记变更点）** | 无 | 无（周期派发） | 无 |
| agent 钻空子空间 | 大 | 极小 | 中（可登记琐碎变更点） | 小 | 大 | 小 |
| agate 现在能自验？ | — | 能 | 能（从下个任务起） | 数据能算，结论不能验 | 不能 | 能（回填 20 次重构） |
| 覆盖"未知的未知" | 否 | **否** | **是** | 部分 | 声称是，实则不可信 | — |
| 平台中立 | 是 | 是（挂载点设计） | 是 | 是 | 是 | 是 |

**乙与丙是互补而非竞争关系**，这是评估的关键结论：

- **乙 管已知约束**：你已经知道"domain 不能依赖 infra"，就把它写成可执行检查，硬拦
- **丙 管未知的未知**：你不知道哪里会烂，靠预测失准把它暴露出来

只做乙会漏掉所有你没想到要检查的东西；只做丙则对已知约束用了过于迂回的手段（明明能硬拦，何必等预测失准）。

## 5. 推荐组合与实施顺序

### 5.1 推荐

**己（使能器）→ 乙（已知约束）→ 丙（未知的未知）；甲作为免费补充；丁、戊推迟。**

顺序理由：

1. **己先做**，因为它是其余所有机制的出口。没有它，任何审视发现的问题都无处安放。且风险最低（形式化既有实践）、不依赖任何其他机制
2. **乙次之**，因为它复用已有的 `gate_commands` 机制，是纯增量、无新概念、可立即在 agate 自身验证（agate 自己就有"脚本不得反向依赖测试"这类可写成检查的约束）
3. **丙最后**，因为它有真实的每任务负担和钻空子面，需要前两者稳定后再引入，且要限定适用范围（§5.2）
4. **丁、戊推迟**，理由见 §0 与 §3

### 5.2 丙的适用范围必须限制（否则违反非目标）

讨论稿非目标明确"不为每个普通功能任务增加固定阶段/负担"。丙确实有每任务负担，所以**不能无条件全量启用**。建议触发条件（满足其一才要求登记 `change_budget`）：

- `risk_level` 为 medium / high，**或**
- P2 引入新模块 / 改动模块边界 / 新增跨模块依赖

低风险的局部改动不要求登记。这样负担落在真正涉及结构决策的任务上。

### 5.3 分阶段计划

**Phase A：重构一等任务（方案己）**
- 产出：`P1-requirements.md` 加 `change_type: refactor` 字段；`phase-cards/P6-acceptance.md` 增加 refactor 口径分支（回归全绿 + 行为不变，禁止伪造功能 BDD）；`check-gate.sh` P6 分支按 `change_type` 分流
- 验收：用 agate 已有的一次真实重构（如 `refactor: trim orchestrator-template.md`）回填走一遍，确认 P6 口径可用
- 止损：若回填时发现 refactor 口径与既有 P6 gate 冲突难以调和 → 停，重新设计而非硬塞

**Phase B：架构约束可执行化（方案乙）**
- 产出：`P2-design.md` 支持 `gate_commands.P5_arch`；`phase-cards/P5-verification.md` 增加执行说明；未声明时**优雅降级为不检查**（与 `P5_formatter` 的既有降级设计一致，不新增拦截）
- 验收：在 agate 自身声明至少一条真实架构约束并跑通。候选：`scripts/` 不得依赖 `tests/`；`phase-cards/` 不得直接引用具体脚本实现细节
- 止损：若 agate 自身写不出任何一条有意义的架构约束 → 说明这个挂载点对文档型项目无用，只对代码型项目有用，应明确标注适用范围而非强推

**Phase C：变更预算预登记（方案丙）**
- 产出：`P2-design.md` 的 `change_budget` 字段 + schema 校验；`P1-requirements.md` 增加"是否命中已登记变更点"勾选；P6 偏差对照与超阈值记录
- 验收：**这是整个主动机制的真验收**——必须有至少一次真实的"预测→后续任务命中→对照"完整发生。在此之前，Phase C 只是登记了一堆未结算的预测，不构成验证
- 止损：见 §6.1 第 3、4 条

## 6. 风险、止损与诚实标注

### 6.1 止损条件

1. Phase A 后，连续 3 次重构仍走协议外的直接 commit → 说明 refactor 流程比直接改更麻烦，流程设计失败，重新设计
2. Phase B 后，agate 自身与首个下游项目**都**写不出有意义的架构约束 → 挂载点无用，移除
3. Phase C 后，连续 10 个任务**没有一次命中**已登记的变更点 → 预测永远不结算，机制退化为纯文书负担，**移除 `change_budget` 强制**
4. Phase C 后，登记的变更点普遍琐碎（如"改个常量"）或预测范围普遍夸大到不可能失准 → 钻空子面已被利用，机制失效，移除而非加码检测

**第 4 条要特别说明**：按 agate 一贯哲学，发现钻空子的正确反应是**移除或重设计机制**，不是加一层检测去抓。纯检测是军备竞赛且是输的策略。

### 6.2 未解决 / 不确定（诚实标注）

1. **丙的钻空子面没有封死**。"要求变更点来自 P1 out-of-scope / roadmap"只是部分缓解——如果 roadmap 本身写得琐碎，照样能规避。**我没有找到不引入人工判断就能封死它的办法。**这是本文最弱的一环
2. **丙的反馈周期长到可能超出项目耐心**。预测在任务 N 登记，可能 N+10 才结算，也可能永不结算。这个机制的价值需要项目持续运行相当长时间才显现，而这一点**无法在引入前验证**
3. **乙对文档型项目可能无用**。agate 自身以 Markdown 为主，"架构约束"是否写得出来存疑——Phase B 验收就是在测这个，但结果未知
4. **全文没有一个方案能主动发现"还没爆雷、也没被预测覆盖"的腐烂**。丙只覆盖被登记的变更点，乙只覆盖已知约束。这块能力缺口是真实存在的，本文没有解法，不应假装有
5. **本文推荐无法在 agate 自身充分验证**。Phase A、B 可以自验，Phase C 的真验收需要多个连续的、走完整 P0-P8 的任务——agate 目前只有 1 个任务有完整归档产出（4.8% commits 走 `wf(` 流程），不产生这种条件。**首个下游项目才是真正的试验场**
6. 本文关于"重构已发生 20 次"的推断基于 commit message 前缀，未逐条核对这些 commit 是否真的是重构（可能有误标）
7. **§0 的每任务波及文件数是用"commit message 含任务编号"归集的，精度有限**：会误收顺带提及该编号的文档 commit，也会漏掉未标编号的相关 commit。这组数字用于说明"数据算得出来但读不懂"是够的，但**不足以支撑任何定量结论**，不应被后续工作直接引用为基线

## 7. 对三个设计张力的直接回答

**张力一：架构审视该由谁做（独立 subagent？周期性？）**

→ **不设常设审视角色，不做周期性派发。**改为**事件触发的一次性派发**：预测偏差超阈值时，派发一次架构复看。

理由：周期派发的问题不只是负担，而是**它产出的东西不可验证**（方案戊）。事件触发则不同——"预测说改 2 处、实际改了 15 处"是客观事实，由它触发的复看有明确的、非空的议题（"为什么差这么多"），而不是漫无目的地问"架构还行吗"。

这与技术债那边的 `retreat` 触发同构：**客观事件触发，不需要任何人先判断"该审视了"**。

**张力二：重构任务怎么进 backlog（谁决定何时重构）**

→ **不靠"谁决定"，靠三个客观触发源汇入**：

| 触发源 | 客观性 | 来自 |
|---|---|---|
| 预测偏差超阈值 | 完全客观（预测 vs 实际） | 本文方案丙 |
| `retreat` 事件 | 完全客观（协议定义的事件） | 技术债那篇 |
| 高优先级债务条目积压 | 半客观（优先级仍是判断） | 技术债那篇 |

三者都不需要"有人觉得该重构了"。**是否真的重构仍由人决定，但"是否要认真考虑一次"由事件强制。**

**张力三："持续优秀"怎么度量**

→ **不度量架构质量（不可度量），度量"我们对自己系统的理解准不准"——即预测准确率。**

这个指标有三个罕见的好性质：

1. **可计算**：预测值与实际值都是文件数/模块数，无需主观打分
2. **抗 Goodhart**：把它做好看的唯一方法是真的把架构做好。往大了预测=自证架构差且会被 P2 评审质疑；往小了预测=会被现实打脸
3. **它度量的东西本身就有意义**：预测持续失准，说明团队不理解自己的系统——按 Ousterhout 的框架，这正是"未知的未知"这一最糟糕的复杂度形态的可观测代理

**但必须配上第 6.2 条第 1 点的诚实标注**：它可以被"只登记琐碎变更点"规避，所以它是一个**在诚实使用前提下有效**的指标，不是一个防作弊的指标。按 §6.1 第 4 条，一旦发现被规避，应移除而非加检测。

## 8. 自我评审记录

按 agate 纪律，self-authored 文档存在 producer=judge 局限，记录自评发现。

**自评发现的第一个问题（已修正）**：初稿把方案丙（变更预算）作为唯一核心，把方案乙（架构约束可执行化）只当作次要补充。自评时发现这是**错的**——两者覆盖的是完全不同的东西：乙管已知约束（能硬拦就该硬拦），丙管未知的未知（只能靠预测失准暴露）。把能硬拦的事情交给迂回的预测机制是设计错误。已改为并列互补，并在 §4 明确说明。

**自评发现的第二个问题（已修正，且是本轮最严重的一处）**：初稿的 §0 断言"agate 只有 1 个已完成任务"，并据此否决了方案丁。**这个前提是错的。**我当时只看了 `active-tasks.md` 的已完成表（确实只列了 T001）就下了结论，没有去 commit 历史里核对。

自评时改用 `git log` 提取任务编号，实测得到 **24 个任务编号（去掉 T001/T091 改名重复后约 23 个）**，且每任务波及文件数完全算得出来。初稿的整个"数据不存在"论证链条因此作废。

**但重做后的结论反而更强**：数据算得出来，却**读不懂**——T019 波及 90 个文件，是架构烂还是任务本来就大？没有基线就无从判断。于是方案丁的否决理由从"没有数据"（错误）变成"有数据也缺解读基线"（正确），而这直接强化了方案丙：**预测提供的正是那个缺失的基线**。这条论证在初稿里完全没有，是自评的产物。

同时修正的还有一处事实错误：初稿称 20 个 refactor commit "全部在任务流程之外"，实测是 **19/20**（有一个引用了 T080）。

**这两轮自评的共同教训**：上一轮是"原型输出看起来合理≠机制有效"，这一轮是"看了一份文档就当成了全部事实"。共同点是**只用了最容易拿到的那份证据，没有交叉核对**。`active-tasks.md` 是一份人工维护的看板，它不完整恰恰是很正常的——我却把它当成了权威事实源。

**自评未能解决的问题（保留在 §6.2）**：方案丙的钻空子面（只登记琐碎变更点）我没有找到不引入人工判断的封死办法。我考虑过要求"变更点必须来自 roadmap"、"必须由独立 subagent 提出"等，前者可被规避、后者把 producer=judge 问题原样搬到另一个 agent 身上。**这是本文最弱的一环，我选择标注而非用一个看似严密实则无效的机制掩盖它。**

**一处刻意的克制**：我没有为"如何检测 change_budget 被敷衍填写"设计检测机制。按 agate 哲学（纯检测是军备竞赛且是输的策略），正确反应是 §6.1 第 4 条的"发现被利用就移除机制"，而不是加一层检测。这是有意为之，不是遗漏。

## 9. 一句话总结

主动机制的根本困难是：**架构好坏没有 ground truth，所以既不能靠 agent 判断，也不能靠机器指标**（后者上一轮已实测证伪）。

本文的出路是**把不可验证的判断换成会被现实结算的预测**，并配一个能硬拦已知约束的挂载点：

- **乙**（`gate_commands.P5_arch`）硬拦你已经知道的约束——复用既有机制，平台中立
- **丙**（`change_budget` 预测-验证）暴露你还不知道的问题——反 Goodhart，从第 1 个任务即可起步
- **己**（重构一等任务）给两者的产出一个出口——形式化已发生 20 次的既有实践

目标形态不是"保证架构优秀"（做不到，别承诺），而是**"让架构问题无法被静默地拖下去"**。

建议下一步：只做 Phase A（重构一等任务），用 agate 已有的真实重构回填验证——成本最低、风险最低、且它是其余机制的前置。
