## 1. 背景

agate 工作流目前对"失败"已有三类处理机制：

- **known-failures**：P5 阶段登记预存失败（非本任务引入），WARNING 级不阻断推进
- **tech-debt（DEBT）**：登记影响未来变更成本的技术债，含关闭判据
- **复盘（retrospective）**：任务结束后分析原因

这三者各自解决了部分问题，但**缺少一个统一、强制的闭环框架**。一个失败被登记后，是否真的"机理清楚、可复现、措施有效、同类不再发生"，没有明确的验收标准。

中国航天质量管理体系中的「双归零」方法，恰好提供了经过数十年工程验证的完整闭环框架，值得借鉴。

## 2. 什么是「双归零」

**归零**：不是"把问题修好"，而是让问题状态恢复到"它从未发生过的状态"——通过彻底查清根因 + 系统性堵漏，保证同类问题不再复发。一句话：**修好一个故障是及格，查清机理 + 举一反三才是归零。**

「双归零」= 两套五条标准，分别对应技术问题和管理问题：

### 2.1 技术归零五条（针对技术故障）

| # | 标准 | 含义 |
|---|------|------|
| 1 | **定位准确** | 准确确定故障发生的部位/环节，精确到点而非大概 |
| 2 | **机理清楚** | 查清根本原因（物理/逻辑层面的"为什么"） |
| 3 | **问题复现** | 通过试验/仿真/数据复现问题，验证定位与机理判断 |
| 4 | **措施有效** | 纠正措施经过验证确实有效，而非"觉得应该有用" |
| 5 | **举一反三** | 把同类问题在全范围排查一遍，防止别处也踩坑 |

### 2.2 管理归零五条（针对管理/流程漏洞）

| # | 标准 | 含义 |
|---|------|------|
| 1 | **过程清楚** | 问题发生的过程和环节查清楚 |
| 2 | **责任明确** | 责任单位/责任人明确 |
| 3 | **措施落实** | 纠正措施真正落地（可追溯） |
| 4 | **严肃处理** | 按规定处理，不和稀泥 |
| 5 | **完善规章** | 修订制度流程，堵住让问题发生的漏洞 |

> 出处：中国航天科技集团质量管理体系，广泛应用于运载火箭、卫星、载人航天等型号的质量问题归零。

## 3. agate 现状 vs 双归零的差距分析

| 归零五条 | agate 现有机制 | 覆盖度 |
|---------|--------------|--------|
| ① 定位准确 | known-failures 表"测试文件/失败数"列 | ✅ 已覆盖 |
| ② 机理清楚 | known-failures"根因"列（自由文本，无强制结构） | 🟡 部分 |
| ③ 问题复现 | **无强制要求**，多数只写根因推断，无复现证据 | ❌ 缺口 |
| ④ 措施有效 | DEBT closed 判据（要求 task_id + P5/P6 证据） | 🟡 部分 |
| ⑤ 举一反三 | **无机制**，同类问题排查没有流程化 | ❌ 缺口 |
| 管理归零（过程/责任/措施/处理/规章） | **几乎空白**，只在复盘里隐含 | ❌ 缺口 |

### 3.1 关键缺口

1. **复现证据缺失**：known-failures 的"根因"列往往是推断，没有"实跑命令 + 结果"的复现证据。缺少这一步，机理判断可能是错的，后续处理建立在错误前提上。
2. **举一反三空白**：一个失败登记后，不会自动触发"同模块/同类模式排查"。同类问题可能在别的测试/模块重复出现而无人察觉。
3. **管理归零缺失**：流程性漏洞（如"为什么测试没拦住""为什么 gate 放行了"）没有强制分析，导致同类流程问题反复发生。

## 4. 落地方案（三档可选）

### 方案 A：模板增强（轻量，改动小）

- known-failures 模板加两列：**复现证据**（要求写实跑命令 + 结果）、**举一反三**（同类排查结论）
- 表头增加一行管理归零简版：过程清楚 + 措施落地

### 方案 B：A + 归零检查单（推荐）

- 新建 `docs/process/return-to-zero.md`：双归零五条 + agate 映射 + 检查单
- P6/P8 遇失败时参考此检查单，AGENTS.md 加一行引用
- 定位类似 env-check-protocol：**参考工具，非强制 gate**

### 方案 C：B + 流程强制（影响所有任务）

- 双归零嵌入 agate gate：known-failures 提交时校验五条齐全
- 复盘强制走归零模板，缺项不通过
- 改动面大，需先经 B 实践积累数据

## 5. 建议与理由

**推荐方案 B（中量）**，理由：

1. **补齐最大缺口**：复现证据 + 举一反三，直接提升 known-failures 质量
2. **渐进风格一致**：归零检查单是"参考"而非"强制"，符合 agate 现有"待实战验证再流程化"的渐进哲学（对应 backlog #16-19 的思路）
3. **不阻塞现有任务**：C 的强约束等 B 实践出数据再决定，避免给所有任务加不成熟的负担

### 5.1 与 PeekView 实践的对应关系（示例）

PeekView 在一次失败处理中已实际走通归零路径，可作为参照模板：

| 归零五条 | 实际动作 |
|---------|---------|
| 定位准确 | 精确到 `mcp-server.spec.ts` 三个断言行号 |
| 机理清楚 | 查源码确认移动端 FileTree 渲染在 Files 抽屉（默认关闭），断言未按行为写 |
| 问题复现 | CDP 实跑复现 3 例失败，stash 对比验证预存失败 |
| 措施有效 | 修改后 14 passed（含 Mobile 3 例） |
| 举一反三 | 顺带发现并登记 DEBT0007（同类 auth 预存失败） |

## 6. 结论

双归零方法论为 agate 的失败处理提供了经过数十年验证的完整闭环框架。建议以**方案 B** 落地：建立归零检查单 + 增强 known-failures 模板，补齐"复现证据"与"举一反三"两个最大缺口，管理归零作为补充维度。待实践积累数据后再评估是否升级为 gate 强制（方案 C）。

## 收编备注（agateon 项目组初评，2026-08-28）

> 立项前 P1 须重做差距盘点，以下为收编时的初步核验结论（对照 `agate/assets/templates/known-failures-template.md`、
> `agate/assets/templates/retrospective-template.md`、`agate/phase-cards/P0-orchestrator.md` 等权威源）：

1. **「复现证据」确为真缺口且价值最高**：known-failures 模板只有 `根因` 自由文本列；补"实跑命令 + 结果"的
   复现证据列，与 P6 `P6-evidence/` + provenance 审计同方向（self-authored gate 防伪，`LIMITATIONS.md` 局限 3），
   成本低、方向已验证。
2. **「举一反三」非全空白**：P0 卡片已有**强制**的「同类/影响面预判」（预防侧）；缺的是**失败登记后的追溯侧**
   （同模块/同类模式再排查）——PeekView 的 DEBT0007 实例即追溯侧实证。
3. **「管理归零」非空白**：复盘模板（TAG0015）已有归因分层（机制缺口/可复用模式/可行动问题）+ frontmatter
   `mechanism_issues`/`execution_issues` + `check-retrospective.py` 异常触发 + RM-AG0042 门槛失败↔retries 对应校验。
   差距是**完整性**而非"空白"。
4. **「责任明确」需改写为「归属明确」**：管理归零第四条直接照搬可能与仓库反追责哲学冲突（"PAUSED 不是失败，
   是正确路由……红灯是工作/设计的问题"）——应归因到可行动层面而非追责个人。
5. **复现证据与举一反三的落点可复用既有机制**（`-tN`/证据目录范式、`agate-feedback.py`/复盘模板出口），
   不发明新结构，符合"不发明新结构"原则。
6. **方案 C（强制 gate）必须等 B 实践数据**：known-failures 本是 WARNING 级不阻断，贸然升级硬校验收益未证、成本必增。
