# subagent 存活可观测性与自主再派发设计（agate 协议增强提案）

> 状态：设计讨论稿（候选 RM 编号待申领）。评审过程存档见 `docs/reviews/review-subagent-liveness-and-self-dispatch-*-20260902.md`（历轮评审按 v1→v4 递增归档）。
> 触发来源：用户实测观察——长尾 subagent（P4 implementer backend 27M tok / 运行超 1 小时）导致主 Agent 无法判断"卡死 vs 仍在正常工作"，曾因等待超时误判并中止仍在运转的 subagent；同时 subagent 内部执行遇到需要多方向排查/多子任务并行推进的场景时，缺乏受控的自主再派发能力，只能自己串行硬扛或提前依赖主 Agent 把批次切得足够小。
> 相关文档：`agate/dispatch-protocol.md`（派发三铁律 / 五模式编排 / 工作量评估五维评级 / 并行规则）、`agate/state-machine.md`（重试与 PAUSED 语义）、`SELF-GATE.md`（触发范围）、`agate/WORKFLOW.md`。

## 1. 问题定义

### 1.1 现状机制

Agateon 当前是单层派发模型：

```text
主 Agent（orchestrator）
  │ 派发（task 工具，dispatch-protocol 三铁律）
  ▼
subagent（执行角色：analyst/architect/implementer/verifier...）
  │ 产出 → 返回"路径 + 一句话摘要"
  ▼
主 Agent 校验产出 + 跑 gate → 更新 .state.yaml
```

主 Agent 对 subagent 的了解仅限于：① 派发时给的 dispatch-context；② subagent 返回时的路径+摘要。**subagent 执行过程本身是黑盒**，这是既有架构的刻意设计（上下文隔离铁律 2/3），不是缺陷，但带来两个未被现有机制覆盖的问题：

### 1.2 问题一：无法区分"卡死"与"仍在正常工作"

实测案例：P4 implementer backend 子任务运行超 1 小时、消耗 27M tok（同批 frontend 子任务 49.7M tok、耗时 6 小时+）。主 Agent 除了"已经等了很久"这个模糊感受外，没有任何客观信号判断该 subagent 是否仍在推进。已发生过的错误模式：**因等待时长超出主观预期，误判 subagent 已挂起并中止，实际上 subagent 仍在正常工作**。

这个问题的根因不是"subagent 该不该写 progress"——即使协议要求 subagent 落盘 progress，也无法保证：① subagent 是否遵从这条要求本身也是不可验证的（黑盒）；② 落盘 progress 需要 subagent 主动执行一次写操作，如果 subagent 正卡在一次长耗时的单一工具调用中（如全量测试跑 xdist），它没有"间隙"去写 progress，这不代表它挂了。

**核心诊断：不能把"进度内容更新"和"进程存活"混为一个信号。** 前者依赖 subagent 配合（不可靠），后者应该是外部客观可测的（不依赖 subagent 配合）。

### 1.3 问题二：批次粒度切分依赖主 Agent 的静态预判，本质上做不准

现有五模式编排（dispatch-protocol.md §派发编排机制）中，模式 4"先理解后拆"已经提供了"先派侦察 subagent 摸清结构再拆分执行"的机制，但这仍然是**主 Agent 层面**的两级派发——侦察结果回到主 Agent，由主 Agent 决定后续批次怎么派。这解决不了下面这类场景：

- 一个已经在执行中的 P4 implementer subagent，写到一半发现某个子模块的实现路径有两种可能方案，需要分头验证哪种更优；
- 一个 P1 analyst subagent 需要同时确认三个独立信息源（现有代码约定、历史 PR 讨论、外部依赖库文档）才能定稿一条 BDD，三者互不依赖，可以并行查但没必要驱动主 Agent 重新走一轮派发；
- 一个 P4 implementer 在实现过程中，越界发现原定"单发"批次实际上包含 3-4 个可并行的独立子块（这类越界发现在实测中大量出现，参见 §1.4 的实测证据）。

这三类场景的共同点是：**"要不要拆、怎么拆"的判断信息只在 subagent 自己执行到那一步时才会浮现**，主 Agent 在派发时刻（无论是初次派发还是模式 4 的侦察阶段）都不掌握这个信息。要求主 Agent 把颗粒度一次性切准，是在要求它预判它结构上不可能预判的东西。

### 1.4 实测证据：现有 dispatch-context 质量已经不低，但批次仍然过大

对照实测的一份 P4 dispatch-context（TPV0095 backend 域，节选自用户提供材料），可以看到：

- 输入文件、行号导航、实现清单（models.py/database.py/services/entry_service.py/star_service.py/share_service.py/team_service.py（新）/api/teams.py（新）/cli.py/client.py）、约束边界（只改 backend/ 目录）均已明确给出，**不是"一句话让 subagent 自己现找"的低质量派发**；
- 但该批次横跨 9 个文件 + 2 个新模块 + 37 条红灯测试转绿，天然可拆成"建模/迁移 → 服务层收敛 → 新模块（team_service+api）→ CLI 线"四段有依赖顺序的子任务；
- **这类可拆分性只有在 P2-design 已经把改动表列全之后才看得清楚，而这份改动表本身是 P2 阶段的产出，不属于派发 P4 时主 Agent 会重新推导的信息**——即便主 Agent 想在派发前做二次拆分，也需要重新读一遍 P2-design 的改动表并做依赖分析，这份分析工作量不比 subagent 自己在执行中做同样判断更低，且会拖慢主 Agent 侧的响应链路。

> **已核实（2026-09-02，peekview 仓库 TPV0095 P2-design.md）**：该任务的 P2 阶段**确实**按既有机制完成了评级与批拆——`dispatch_plan: {mode: static-batch, parallel_limit: 3}`，三批（backend=high / frontend=medium / mcp=low），且明文"存在 high → 必须拆批"。但 **backend 批内部（9 文件 + 2 新模块）没有再细分**：其内容（models/database/entry_service/star/share/team_service/api/teams/main/cli/client/exceptions）横跨本文所述的"建模/迁移 → 服务层收敛 → 新模块 → CLI 线"四段，而 P2 只把它作为一个 high 批整体声明。这正好落在可能性 B：**静态五维评级正确执行了"跨域批拆"，却捕捉不到批内部的顺序依赖粒度**——后者的拆分信息只在 subagent 读懂 P2-design 实现细节后才浮现。

### 1.5 核验：这是既有机制执行缺口，还是真正的结构性空白

在把 §1.4 的观察当作本设计的立论依据之前，必须先区分两种可能性，否则会把"既有机制未被正确执行"误包装成"需要新机制"：

- **可能性 A（执行纪律问题，非本设计范畴）**：按 `dispatch-protocol.md` §1 工作量评估五维评级，该批次产出规模（9 文件+2 新模块，超过 medium 上限）、耦合度（与 entry_service/star_service/share_service 三个既有模块耦合，落入"≥3 个模块耦合"档）均满足 high 判据。按现有规则"任一维 high → 整体 high，必须拆分"，且该评级理应在 **P2 阶段**做出并声明 `dispatch_plan`（全阶段适用表：P2 行"非 P2 自身拆分——P2 评估并声明后续阶段的编排方案"）。若该实测案例的 P2-design.md 已经声明了 high 评级和拆分方案，但主 Agent 派发 P4 时未遵照执行（仍单发整批），**这是既有机制的执行纪律问题，本设计不解决这类问题，也不应该被拿来当论据**。
- **可能性 B（真正的结构性空白，本设计要解决的）**：若 P2 阶段的五维评级本身无法捕捉这类拆分需求——例如四段子任务（建模迁移/服务层收敛/新模块/CLI）之间的强依赖顺序，只有 subagent 真正读懂 P2-design 细节、动手实现到某一步时才会清晰浮现，静态评级维度（产出规模/输入规模/改动性质/耦合度/认知负荷）无法在派发前完全预判这种**顺序依赖粒度**——这才是结构性空白，是本设计的立论基础。

**本设计明确将自身范围限定为可能性 B**：即"P2 评级与 `dispatch_plan` 声明已经正确完成（或至少不因缺少本设计而无法完成）"的前提下，subagent 在执行中进一步发现的、静态评级维度无法捕捉的动态拆分需求。若某个具体案例的根因实际是可能性 A，应作为独立的技术债登记（既有五维评级执行/校验缺口），不与本设计混同，也不应作为本设计的证据材料使用。

**TPV0095 案例的核实结论**：其 P2-design.md 已核实声明 `dispatch_plan`（static-batch，backend=high）——**不是可能性 A**（P2 评级与批拆机制被正确执行，主 Agent 也按三批派发）；真正的问题正是可能性 B：**high 批内部的顺序依赖粒度（backend 批内四段）未被静态评级捕捉**，只有 subagent 执行中才能发现。该案例为本设计的立论素材成立，无需更换。

结论：**批次粒度问题里属于可能性 B 的部分，不是靠"主 Agent 派发前更仔细地看一遍"能稳定解决的**，需要给 subagent 一个在执行中"发现该拆时就地拆"的机制；属于可能性 A 的部分则应通过既有机制的执行纪律强化解决，不在本设计范围内。

## 2. 设计目标与非目标

### 目标

1. 主 Agent 能用**客观、不依赖 subagent 配合**的信号，区分"仍在正常工作"与"已挂起/卡死"，消除因等待时长主观判断导致的误杀。
2. 执行角色 subagent 在执行过程中，遇到**自己判断适合拆分/并行/多方向探查**的子任务时，具备受控的自主再派发能力，不需要中止当前执行、退回主 Agent 请示。
3. 上述两项能力**不产生新的编排层级**——对主 Agent 和 `state-machine.md` 而言，一个自主再派发的 subagent 内部无论派了几层子任务，外部观感仍然是"一个 subagent 在跑"，不修改现有单层状态机模型。

### 非目标

- 不试图让主 Agent 变得能精确预判批次粒度（§1.3 已论证这在结构上不可行，本设计是绕开这个问题，不是解决它）。
- 不提供"心跳"以外的进度语义解释能力——判断 subagent 卡在哪一步、为什么慢，仍然是 subagent 自己 progress.md 的职责范围，本设计不替代它，只是不再让主 Agent 的生死判断依赖它。
- 不改变 `dispatch-protocol.md` 现有五模式编排语义（模式 4"先理解后拆"仍然是主 Agent 层面两级派发的权威机制，本设计新增的是 subagent 内部一层，两者并存，不合并、不互相替代）。
- 不改变 `check-gate.py` / `check-state-transition.py` 现有 exit 三态约定（0/1/2）。

## 3. 设计一：心跳机制（存活可观测性）

### 3.1 核心原则

**心跳信号必须由外部包装产生，不依赖 subagent 主动配合写入。** 这与 BDD-9"判定可执行化"（质量判断从模型自律转移到脚本强制）是同一哲学在"存活判断"场景下的应用。

### 3.2 前提澄清：派发模型决定心跳机制能不能用

早期版本的心跳设计隐含假设了"主 Agent 派发后可以周期性主动检查心跳文件"，但这个假设**只在部分平台成立**，必须先按派发模型分裂设计，不能用一套机制套所有平台：

**关键事实（`dispatch-protocol.md` 铁律 1 与"Playwright/长时操作 subagent 派发策略"节）**：
- 主 Agent 派发 subagent 是通过**平台工具调用**（Claude Code/OpenCode 的 task 工具，语义是"派发"不是"执行"），**不是 shell 命令**——工具调用不能被 shell 脚本"包装"，早期方案给出的 `agate-heartbeat-wrap.sh` 用 `"$@"` 包裹"派发命令"的写法，是对派发载体的误判，这个示例本身不成立，需要整体替换。
- 更根本的问题：`dispatch-protocol.md` 明确记录"Task 工具本身无超时参数，subagent 内部脚本挂起会无限阻塞主 Agent"，并给出了既定解法——**拆分为可预期耗时的小步骤，不依赖超时/轮询机制**（Playwright/长时操作节的拆分表）。这说明协议作者早就确认过"主 Agent 在等待 task 工具返回期间，没有余力去做任何其他动作（包括读心跳文件）"这一事实，Claude Code/OpenCode 的 task 工具调用是**阻塞式**的。

据此，心跳机制在不同派发模型下的可用性完全不同，必须分开设计：

| 派发模型 | 主 Agent 能否在等待期间主动检查心跳 | 心跳机制的定位 |
|---|---|---|
| **异步派发**（DSH `subagent`/`subagent_fork` 的后台模式）| 能——DSH 的后台派发本身允许主 Agent 继续执行、周期轮询任务状态 | 心跳三支判定（新鲜/过期/从未心跳，见 §3.3）**按原方案成立**，主 Agent 周期读取心跳文件，主动发现卡死 |
| **阻塞派发**（Claude Code/OpenCode 的 task 工具）| 不能——主 Agent 调用 task 工具后处于阻塞等待，没有"顺便读文件"的执行机会 | 心跳机制**降级**为"中止前二次确认"信号，不是"主动发现卡死"的手段：主 Agent 依然要靠既有的"拆分+预期耗时"（`dispatch-protocol.md` 既定解法）来控制单次派发的耗时上界；心跳只在主 Agent **因为超出预期耗时、已经主观决定要考虑中止**时，作为最后一道核查（见 §3.4）——查一下 subagent 内部自己维护的心跳文件是否最近仍有更新，避免"预期耗时评估过于保守导致误杀" |

**本设计不再假设三平台共用一套心跳检查时机**，§3.3（异步路径）/§3.4（阻塞路径）分开表述。

### 3.3 异步派发平台：心跳轮询（DSH）

DSH 的后台 subagent（`subagent`/`subagent_fork`）派发后，主 Agent 可以继续执行（读状态、处理其他任务）并周期性检查该子任务的心跳文件。心跳产生方式：由 subagent 自身的执行环境（DSH 后台任务本身具备生命周期钩子）在启动时附带一个心跳写入动作，而非由主 Agent 侧包装 shell 脚本产生（这也是对早期载体设计的修正：心跳的产生者应该尽量贴近 subagent 自身的执行环境，而不是主 Agent 侧包一层它自己都无法验证是否真正围住了 subagent 生命周期的 shell 脚本）。

主 Agent 侧判定分三支：

- **心跳新鲜**（mtime 距今未超过阈值，建议默认 3 个周期）：**无论已运行多久、无论 progress 是否更新，都不判定为卡死**，时长本身不再是判杀依据，正常等待。
- **心跳过期**（曾经产生过心跳文件，但最近一次 mtime 超过阈值未更新）：判定为进程真正挂起/崩溃，此时中止是安全的（可选配套：中止前用平台自带的会话/任务状态查询做一次二次确认，避免心跳文件被文件系统延迟写入等边缘情况误判）。
- **从未心跳**（派发后经过一个"启动宽限期"，心跳文件仍未出现过）：**不等同于"心跳过期"**——这种情况更可能是心跳产生机制本身未能正常挂载（DSH 后台任务钩子配置问题等），属于**派发失败**，应走既有的"subagent 返回校验"重派流程（`dispatch-protocol.md` 已有机制），而不是当作"执行卡死"处理。启动宽限期建议默认为 1 个心跳周期。

### 3.4 阻塞派发平台：心跳降级为中止前二次确认（Claude Code / OpenCode）

对 Claude Code/OpenCode 的 task 工具派发，主 Agent 阻塞等待期间**没有执行机会**去做任何轮询，§3.3 的三支判定在这个模型下不成立。真正能落地的用法是：

1. **主线仍然依赖 `dispatch-protocol.md` 既定的"拆分+预期耗时"机制**——这是本设计不能替代、也不需要替代的既有解法，本设计只补充它的一个盲区：预期耗时评估本身可能不准（尤其是像本文档 §1.4 提到的实测案例那种大批次），导致主 Agent 在"预期耗时已过但 subagent 仍在正常工作"时产生误杀冲动。
2. **心跳此时的作用是给"要不要中止"这个主观判断提供一个客观参考，而不是主动触发中止判断**。具体方式：subagent 在自己的执行环境内（如果平台的 bash 工具支持后台进程），自行维护一个心跳文件，不依赖主 Agent 侧包装；当主 Agent 因为等待时间明显超出该批次的预期耗时评估、开始考虑是否要中止时，**在真正执行中止动作之前**，先检查该心跳文件的存在与新鲜度——如果最近仍有更新，说明 subagent 大概率仍在正常推进，不应中止；如果心跳过期或从未出现，才继续中止流程。这本质上是给"中止"这个动作加一道客观核查，而不是把心跳当成主动发现卡死的信号源（因为在阻塞模型下，主 Agent 根本没有主动发现的执行窗口——它只能在"已经决定要检查"的那个时间点，也就是它自己因超时而醒来采取行动的那一刻，去看一眼心跳）。
3. **心跳文件谁来产生**：在阻塞模型下，主 Agent 无法在派发的同时另起一个包装进程去 touch 心跳文件（因为它自己就阻塞在 task 工具调用里）。心跳必须由 **subagent 自己**在其被派发后的执行过程中，用它自己可用的工具（bash 后台进程）产生，并写入约定路径。这要求在 dispatch-context 的 prompt 中，对预期耗时较长的批次显式要求 subagent 自行起一个心跳后台进程——这是对 subagent 行为的**约定**，不再是"外部客观产生、不依赖 subagent 配合"的强保证（这一点与 §3.1 的核心原则出现了必要的妥协，需要显式说明，不能掩盖）。

### 3.4.1 后台心跳进程能否检测"卡死"：按阻塞发生的层级区分

subagent 自行起的心跳后台进程，能不能真的探测出"卡死"，取决于卡死发生在哪一层，不能一概而论：

| 卡死类型 | 后台心跳进程是否也跟着停 | 心跳能否检测出这类卡死 |
|---|---|---|
| **subagent 所在会话/进程本身被杀死或异常退出**（如宿主进程崩溃、被系统 OOM kill、平台会话被强制终止）| 会——后台心跳进程通常是该会话/进程的子进程，父进程死亡后子进程要么被一并回收（进程组终止），要么成为孤儿进程但通常也会因为宿主环境清理而终止 | **能**。这是心跳机制真正有效的场景：会话整体消失，心跳自然停止，主 Agent 能可靠判定为真死 |
| **subagent 卡在单次工具调用的系统调用层面无限阻塞**（如一次网络请求没有超时、一次文件锁等待）| **不一定**——如果这次阻塞的工具调用和心跳后台进程是同一个操作系统进程内的不同线程/子进程，且没有共享会导致两者一起卡住的资源（如同一把文件锁、同一个被打满的 CPU 核），心跳后台进程可以继续独立运行，不受影响 | **能**，但依赖"心跳进程与被阻塞的调用互相独立"这个前提——如果两者共享了会导致联动卡死的资源（比如都要等同一把锁、或者整个容器 CPU 被单个失控循环打满导致所有进程都调度不到），心跳也会跟着变得不新鲜，这种情况下反而是心跳机制的**加分项**（能检测出"资源层面的整体阻塞"，不只是"单个调用挂起"）|
| **subagent 逻辑上陷入原地打转**（如反复重试同一个失败操作、陷入死循环但循环体本身很轻量、没有真正阻塞任何系统调用）| **不会**——只要 subagent 所在进程本身还在正常调度、CPU 没被打满，后台心跳进程可以正常继续 touch 文件 | **不能**。这是心跳机制的**盲区**：进程活着、心跳新鲜，但 subagent 在做无意义的空转，没有实质推进。心跳只能证明"进程存活"，不能证明"进展有效"——这个盲区本设计不解决，需要依赖 subagent 自己的 progress 内容或者外部对产出文件变化的观察来补充判断，不属于本设计范围（见 §2 非目标） |

**结论**：你提出的机制——"subagent 卡死则心跳自然跟着卡死，因此可以用心跳检测"——在**进程级/会话级**的卡死场景下成立，这也是心跳机制设计初衷主要覆盖的场景（对应实测案例里"等了一小时不知道是死是活"的典型情况，通常就是会话层面的问题，不是逻辑空转）。但心跳机制不能覆盖"进程活着但逻辑空转"这类卡死，这类问题的信号应该是"心跳新鲜但长时间没有任何产出文件变化"，属于心跳机制之外的另一种观察维度，本设计不在此展开，留待后续设计（可能与 progress.md 内容观察机制结合）。

> **诚实边界声明**：§3.1 的核心原则（心跳外部产生、不依赖 subagent 配合）**只在异步派发平台（DSH）完全成立**。在阻塞派发平台（Claude Code/OpenCode），由于主 Agent 自身处于阻塞状态、无法另起进程包装派发过程，心跳的产生退化为"约定 subagent 自行维护"，其可靠性弱于 DSH 路径（subagent 若不配合，心跳依然缺失，此时主 Agent 只能退回纯粹依赖"拆分+预期耗时"的既有机制，不产生新的风险敞口，但也不产生新的收益）。这是设计上的诚实妥协，不是缺陷——完全消除对 subagent 配合的依赖，在阻塞派发模型下没有可行路径，除非平台本身提供进程外监控能力（目前三平台均未提供）。此外，即使 subagent 配合起了心跳进程，该机制的检测范围也**仅限于进程级/会话级卡死（§3.4.1 表格第一、二行），不覆盖逻辑空转（第三行）**——这是心跳机制本身的天然边界，不是阻塞路径独有的弱化。

### 3.5 心跳文件的生命周期定义

心跳文件一旦落盘到 `agate-workspace/tasks/` 目录下，即进入协议管辖的文件系统命名空间，需要明确规范，避免与既有审计脚本产生冲突或噪音。本节的命名/清理规范对 §3.3（DSH 异步路径）与 §3.4（阻塞路径 subagent 自维护）产生的心跳文件同样适用——两条路径的心跳"产生者"不同，但落盘之后的文件系统管理规则应统一，避免出现两套命名习惯。若父 subagent 在 §4 自主再派发场景中又给子任务维护了心跳（无论走哪条路径），同样遵循本节的父子分层命名规则：

1. **命名规范，父子分层**：任务级心跳文件固定为 `${TASK_DIR}/.heartbeat`；若父 subagent 内部又给子任务包心跳（§4 自主再派发场景），子任务心跳文件命名为 `${TASK_DIR}/.heartbeat.child-{n}`（`{n}` 为子任务序号，父 subagent 自行分配，不需要全局唯一，仅需在同一父任务内不重复），避免同名覆盖。
2. **审计豁免**：`.heartbeat*` 类文件属于运行时临时信号，不是任务产出物，不计入 `check-p6-provenance.py` 审计范围，也不计入 `check-protocol-consistency.py` 的文档一致性扫描对象——两者的扫描对象定义（协议文档/产出文件）本身不包含以 `.` 开头的运行时文件，理论上默认不会被扫到；落地时需在对应脚本的路径过滤逻辑中显式确认这一点并登记确认结果，不能假设"默认不扫"就足够，需要有一条可核验的记录。
3. **清理时机**：任务结束（无论成功/失败/超限）后，负责产生心跳的一方（DSH 路径下是后台任务钩子，阻塞路径下是 subagent 自身）应清理自己产生的心跳文件；若异常中止导致未能清理，遗留的心跳文件在下次同任务重新派发前，由派发前置检查清空（比照 `agate-archive-stale-outputs.py` 现有的任务目录收尾清理模式，不需要新造一套清理机制）。

### 3.6 影响面

- `dispatch-protocol.md`：新增一节说明异步/阻塞两条心跳路径的判定时机差异，并明确本设计与既有"Playwright/长时操作 subagent 派发策略"（拆分+预期耗时）节的关系——本设计是该既定机制在"预期耗时评估不准"时的补充核查手段，不替代它。
- DSH 路径：需要确认 `subagent`/`subagent_fork` 的后台任务钩子机制具体如何附加心跳写入动作，需要一次实机验证（比照 `platform-notes.md` 对 DSH 的既有实机验证惯例）。
- 阻塞路径：需要在 dispatch-context 派发模板中，为预期耗时较长的批次新增一条"自行维护心跳文件"的约定指导，并明确这是对 subagent 的行为约定而非外部强制信号（§3.4 诚实边界声明）。
- 不修改 `check-gate.py`/`check-state-transition.py` 返回约定，心跳判定与 gate 判定是两套独立信号，互不干扰。
- 心跳阈值、周期作为可配置项（类似 `maintainability.yaml` 的既有模式），缺失/损坏时兜底为默认值，不报错。

## 4. 设计二：受控的自主再派发（子派发权限下放）

### 4.1 核心原则

**权限下放给执行角色，但子派发的产出必须完全收敛回父 subagent 自己承担的 gate 责任，不产生跨层状态外泄。**

具体表达为两条不可违反的边界：

1. **子任务不写 `.state.yaml` / `active-tasks.md`**，不产生独立的 phase 状态。子任务的存在、数量、内部分工对主 Agent 和状态机完全不可见——外部观感永远是"一个 P{n} 角色 subagent 在跑"。父 subagent 汇总子任务产出后，仍然只能通过自己被派发时约定的"路径+摘要"格式向主 Agent 汇报，不允许把子任务列表当作新的汇报单元。
2. **子任务的写权限是父 subagent 权限的严格子集**，不能扩大。例如父 subagent 被约束"只改 backend/ 目录"，其派出的子任务同样只能触碰 backend/ 目录内的文件，这条约束必须由父 subagent 在派子任务的 prompt 里显式重申，不能假设子任务会自动继承。

### 4.2 与既有模式 4（先理解后拆）的关系：互补不替代

| | 模式 4（先理解后拆，既有机制） | 本设计（subagent 自主再派发，新增） |
|---|---|---|
| 派发层级 | 主 Agent → 侦察 subagent → 主 Agent → 执行 subagent（两级，均由主 Agent 发起） | subagent → 子任务（一级，主 Agent 不感知） |
| 决策时机 | 派发前（主 Agent 收到侦察结果后决定怎么拆） | 执行中（subagent 自己发现该拆时就地决定） |
| 是否影响状态机 | 是（侦察和执行分属同一 phase 内的两次独立派发，主 Agent 需要分别校验产出） | 否（对状态机而言仍是一次派发） |
| 适用场景 | 派发前就能预判"工作量 high / 结构不明"，值得提前投入一次侦察 | 派发时看不出、只有执行到一半才浮现的拆分需求 |

两者不冲突：一个 P4 批次可以先经过模式 4 的侦察-执行两级派发，执行阶段的某个 subagent 又在内部触发本设计的自主再派发——这是两层不同粒度的机制叠加，不是二选一。

### 4.3 平台差异（挂实现注记）

> 实现注记：以下能力现状经核实（2026-09-02），三平台机制随版本可能变化，需持续复核（参照 `platform-notes.md` 对 DSH 的既有复核惯例）。

| 平台 | 现状 | 落地方式 |
|------|------|----------|
| Claude Code | 原生支持 subagent 内调用 Agent 工具再派子任务；需在角色 frontmatter 的 `tools` 字段显式包含 `Agent` 才能启用（默认不带）；存在嵌套深度上限（默认 5 层）与并发数上限（默认 20，超限报错不重试） | 在需要开放此能力的角色定义（如 P4 implementer 角色卡）中显式声明 `tools` 含 `Agent`；派发 prompt 中重申 §4.1 两条边界 |
| OpenCode | 自定义角色的 subagent 当前被框架在权限层硬性禁用 Task 工具（`task: false` 强制，frontmatter 声明 `permission: {task: allow}` 无效，已有相关 issue 追踪）；仅框架内置的 `explore`/`general` 代理理论上可再派发，但缺乏深度限制，存在失控风险 | 不依赖框架级嵌套。改用进程级调用：subagent 通过其自带的 bash 工具，以 CLI 方式（如 `opencode run "..."`）并行拉起只读子查询，结果通过重定向文件收集。**严格限定用途**：仅用于不写文件、不碰 git、不触发 gate 的信息收集类子任务；子任务产出"用后即弃"（不落盘为任务交付物的一部分），不作为可审计产出使用。此用法本身不需要等待 OpenCode 官方开放嵌套能力。**注**：`opencode run` 的具体命令行参数、阻塞行为、独立会话状态处理方式尚未在本仓库环境实测验证，落地前需要一次实机验证（比照 `platform-notes.md` 对 DSH 的实机验证惯例），且该 CLI 行为随 OpenCode 版本变化的风险需要纳入 §5 风险表持续跟踪 |
| DSH | 架构原生支持，`subagent`/`subagent_fork` 提供两种上下文模式（独立 vs 继承），`workflow` 层提供更高阶的多子调用编排（暂停恢复、证据留痕）；平台仍处于 Developer Preview，机制随版本可能有破坏性变更 | `subagent_fork`（继承上下文）适合子任务需要共享父任务当前进度的场景；`subagent`（独立上下文）适合真正隔离的并行探查；接入方式沿用 `dsh-integration.md` 现有能力矩阵的记录惯例，每次核实需注明验证的具体版本号 |

### 4.4 P6.5 judge 类角色的例外声明

独立 judge（`design-independent-judge.md`）以及其他要求 fresh context 信息隔离的角色（防造假三层防线之一）**不适用本设计**。

需要明确论证冲突点，而不能只归因为"开放性冲突"这种笼统表述：judge 角色的核心设计约束是"复核结论仅能基于其自身独立获取的证据，不能受主线执行过程中产生的判断污染"（防伪造三层防线之一）。如果允许 judge 自主派发子任务，即便子任务本身也是 fresh context，**判断"要不要派子任务去查什么、怎么解读子任务返回的结果"这个决策本身，仍然是 judge 主观认知过程的一部分**——子派发不是把判断转移给了一个完全中立的外部信号源（像 gate 脚本的 exit code 那样客观），而是 judge 自己决定"该查什么方向"，这个决策路径选择本身可能被诱导或产生确认偏误（即 judge 倾向于派发能验证自己已有倾向的子查询）。这与 judge 存在的意义（提供一个不受主线判断路径影响的独立复核）直接冲突。相比之下，普通执行角色（P1-P5 的 analyst/architect/implementer/verifier）本身就需要做主观判断和权衡，子派发只是延伸了它们已有的"自主决定怎么干活"的权限边界，不产生新的性质冲突。

因此，本设计的子派发权限只对普通执行角色开放，judge 类角色的信息隔离要求与"自主再派发"的决策路径开放性存在性质冲突，不得开放 Agent/subagent_fork 工具权限。派发 judge 角色时应显式在角色定义或 dispatch-context 中声明"不启用子派发能力"，避免误开放。

### 4.5 影响面

- `agate/dispatch-protocol.md`：新增一节说明本设计与既有五模式的关系（§4.2 表格内容并入）。
- 各执行角色的 phase-card（P1 analyst / P2 architect / P4 implementer 等，不含 judge 类角色）：按需新增"子派发权限声明"字段，默认不开启，需要时显式声明。
- `platform-notes.md`：新增能力矩阵行，记录三平台子派发支持现状（对应本文 §4.3 表格，作为该文档的权威源引用点）。
- 不修改 `check-gate.py`/`check-state-transition.py`；子派发产生的任何中间产出不计入 gate 判定对象，只有父 subagent 最终声明的 `files_modified` 才走既有的假完成校验（D2，见 `dispatch-protocol.md`）。
- 触发 `SELF-GATE.md`（改动涉及 `agate/*.md` 协议文档与 phase-card），需按既有流程走 protocol-alignment-review。

## 5. 风险与止损

| 风险 | 止损 |
|------|------|
| 心跳包装脚本本身崩溃/未启动，导致心跳文件永不产生 | 主 Agent 侧对"心跳文件从未出现"（而非"过期"）单独处理：区分"从未心跳"（可能是包装脚本本身没跑起来，应视为派发失败而非执行卡死）与"曾心跳后过期"（真正的执行卡死），两种情况的重试/止损路径不同 |
| 心跳阈值设置过短，正常的长耗时单一工具调用（如全量 xdist 测试）被误判过期 | 阈值默认值需要覆盖已知最长的单次工具调用耗时留出安全余量；可配置项覆盖默认值，且缺失/损坏时兜底默认值不报错（参照 `maintainability.yaml` 既有模式） |
| OpenCode 路线（CLI 子进程）被滥用为正式编排层，产出被当作可审计交付物 | §4.3 已明确限定"仅用于只读信息收集、用后即弃"；若需要正式编排地位，应退回 §4.2 表格里"模式 4"的主 Agent 层面机制，不得用 CLI 子进程冒充 |
| OpenCode `opencode run` 具体命令行为（阻塞方式/参数/独立会话状态）未经本仓库实测，落地后随版本变化可能导致子查询静默失败或行为漂移 | 落地前先做一次实机验证并记录验证版本号（比照 `platform-notes.md` 对 DSH 的实机验证惯例）；纳入日常复核节奏，版本升级后重新验证 |
| Claude Code 嵌套深度/并发上限的默认值随版本变化（已有社区案例因版本升级导致默认行为改变而中断嵌套流水线）| `platform-notes.md` 对应条目需注明验证版本号，比照 DSH 现有"新兴平台需持续复核"的记录惯例；升级前建议先在非生产任务上验证嵌套行为未回归 |
| 子派发权限被误开放给 judge 类角色，破坏信息隔离防线 | §4.4 显式声明例外；phase-card 层面 judge 角色的工具声明默认不含 Agent/subagent_fork，需要人工显式修改才能违反，非默认行为 |
| 子任务写权限意外超出父 subagent 权限范围 | §4.1 第二条边界要求父 subagent 在派子任务 prompt 中显式重申约束；后续可考虑配套一个轻量校验（子任务返回的 `files_modified` 路径校验，复用既有 D2 机制的路径校验逻辑，见 `dispatch-protocol.md` 第 7 条）|
