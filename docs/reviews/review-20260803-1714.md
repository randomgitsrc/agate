## 2. BLOCKING：Task 2 Step 3 的插入点描述有歧义，字面执行可能导致 P3 兜底在 --no-verify 场景下完全失效

这是本次评审最重要的发现。

### 2.1 问题

Plan 原文（Task 2 Step 3）：

> 在 `run_gate` 之后、`main` 中，当 phase == P3 时额外跑 check-tdd-red.sh：
> 在 main() 中 `ci_exit, ci_output = run_gate(phase, task_dir)` 之后追加：

我读了 `ci-gate-backstop.py` 的真实控制流（第 84 行 `ci_exit, ci_output = run_gate(...)` 之后）：

```python
ci_exit, ci_output = run_gate(phase, task_dir)

if not gate_result.exists():
    if ci_exit == 1:
        print(...)
        return 1
    print(f"WARN: 无 .gate-result.json（可能 --no-verify 跳过），CI exit={ci_exit}")
    return 0                          # ← --no-verify 场景下，函数在这里就 return 了

with open(gate_result) as f:
    recorded = json.load(f)
...
if recorded_phase != phase:
    return 1                          # ← 又一个 return
if recorded_exit != ci_exit:
    return 1                          # ← 又一个 return
...
print(f"PASS: phase={phase} exit_code={ci_exit} 一致")
# P6 provenance audit ...
# provenance 审计兜底 ...
return 0
```

**"在 `ci_exit, ci_output = run_gate(...)` 之后追加"这句话在字面上最直接的读法，是紧跟在这一行代码后面插入**——如果真的这样做，P3 检查会在所有后续的 `return` 之前执行，这是安全的（能覆盖 --no-verify 场景）。但 plan 给出的完整代码片段是一段独立的 `if phase == "P3": ...` 块，并没有明确说"这段要插在 `gate_result.exists()` 判断之前还是之后"，也没有说明"如果之后所有分支都 return 了，这段代码是否还会被执行到"。

**如果实施者读到"main() 中...之后追加"这句话，选择把这段代码放在函数体最后（`return 0` 之前，即整个函数的末尾，这是很多人写 Python 时"追加逻辑"的直觉位置）**，那么：
- 当 `.gate-result.json` 不存在（也就是 T085 复盘里真实发生过的 `--no-verify` 场景）时，函数会在 `return 0`（"WARN: 无 .gate-result.json"分支）处提前退出，**永远不会执行到函数末尾的 P3 检查代码**。
- 而 `--no-verify` 绕过 hook、导致 P3 红灯没有被真实验证，恰恰是 T085 复盘要修的核心问题，也是这份 plan 的 Architecture 一节反复强调"CI backstop 兜底"的场景。

**换句话说：如果实施时选错了插入位置（一个很容易选错、且 plan 文字没有明确排除的位置），P3 检查的兜底效果在最需要它的那个场景（--no-verify）里会完全失效，而 bats 测试可能还是绿的**——因为 plan Task 2 Step 6 给出的 4 个新测试（`backstop P3: 真红灯/绿灯/假红灯/无运行器`）全部是通过 `setup_git_repo_p3` 手工构造了 `.state.yaml` 和文件，**没有一个测试模拟"没有 `.gate-result.json`（即 --no-verify 场景）"**，所以就算实施者把代码放在错误的位置，这 4 个新测试依然会全部通过（它们测的是"P3 分支本身工作"，不是"P3 分支在 --no-verify 路径下依然被执行到"）。

### 2.2 已有先例：文件末尾的 provenance 审计正是这个问题的活证据

`ci-gate-backstop.py` 现有的"P6 provenance audit"和"provenance 审计兜底"两段代码，就位于函数最末尾（`return 0` 之前）。这两段代码**目前就只在 `.gate-result.json` 存在且校验通过的路径下才会执行**——如果 `--no-verify` 被使用，这两个已有的审计同样不会被触发。这不是我猜测的风险，是这份代码库里已经存在的真实行为，可以直接读代码确认（本次评审已经读过，见上面贴出的完整控制流）。

**这意味着：如果 Task 2 的实施者参照现有代码"追加在函数末尾"的写法习惯（大概率会，因为这是本文件里所有先例的写法），P3 检查就会重蹈同样的覆辙——变成又一个只在"一切正常"时才生效、而在 `--no-verify` 这个真正需要兜底的场景下形同虚设的检查。**

### 2.3 建议修复

Plan 需要在 Task 2 Step 3 里明确写清楚插入位置，建议改为如下表述：

> 在 `ci_exit, ci_output = run_gate(phase, task_dir)` **这一行之后、`if not gate_result.exists(): ...` 判断之前**插入 P3 检查代码。P3 检查必须在任何 `.gate-result.json` 存在性判断之前执行，因为 `--no-verify` 场景（`.gate-result.json` 不存在）正是 T085 复盘要覆盖的核心场景——如果放在函数末尾，会重蹈现有 P6 provenance audit 的覆辙（那两段审计目前也只在 `.gate-result.json` 校验通过后才执行，对 `--no-verify` 场景无效，这是本次评审读代码时发现的、与本 plan 无关的既有行为，建议一并记录到 roadmap 供未来考虑，但不要求本次一并修）。

同时建议 Task 2 Step 6 补一个测试（可命名为 `backstop P3: 无 .gate-result.json（--no-verify）时仍执行 check-tdd-red.sh`），显式验证插入位置的正确性，而不是只测"P3 分支本身逻辑对不对"。

## 3. SHOULD_FIX：check-state-transition.sh 检查 3 删除的安全性，已用实测验证，plan 的说法准确，但建议补充这一验证证据

Plan 声称"删除检查 3 后，检查 4 不受影响，因为 `diff` 变量仍在检查 1 中计算"。

我没有只读代码就采信这句话，而是做了实测：把检查 3（L106-155）从脚本中物理删除，跑现有的完整 `check-state-transition.bats`（26 个测试，删除前是这份文件的全部测试）。结果：

- **`ST_ARCHIVE.1` 到 `ST_ARCHIVE.6`（检查 4 相关的全部 6 个测试）在删除检查 3 后依然全部通过**，证实检查 4 对 `diff` 变量的依赖确实不受检查 3 删除影响。
- `ST.17`/`ST.18` 按预期失败（因为这两个测试编码的是旧语义"未 commit 则 exit 1"，plan 本来就要求把它们改写为 exit 0）——这是符合 TDD "先红后绿" 预期的失败，不是意外故障。

**结论**：plan 关于检查 3/检查 4 独立性的技术判断是正确的，这一点我一开始也曾怀疑（`diff` 是在检查 1 的 `if` 块内部计算的局部变量，删除检查 3 后是否还能被检查 4 读到，看代码容易产生疑虑），但实测证明是安全的——检查 3 和检查 4 是通过 `diff` 符号（`diff≥2`→检查1处理、`diff==1`→检查4处理、检查3自己用`new_num>old_num`即`diff<0`）互斥触发的，删除检查 3 不影响 `diff` 本身的计算和作用域。

这不算一个需要修的问题，只是建议 plan 在 Task 1 Step 4 里补一句"已用删除检查 3 后跑 ST_ARCHIVE.1-6 全通过验证独立性"，把这个实测证据写进 plan 本身，而不是仅停留在"注释解释"的层面——这样未来的实施者不需要重新做我做的这次实测就能确认安全性。
