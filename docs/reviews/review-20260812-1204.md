# 对《agate 项目生命周期演进框架讨论稿》的评审与下一步计划

> 本文是对讨论稿的独立回应，不是批准实施的决定。第 1-3 节为评审意见，第 4-7 节为可执行计划。
> 计划部分若被采纳，仍需走完整 P0-P8 立项，本文不替代 P1/P2。
>
> **本文经过一轮自我评审，且自评推翻了初稿的核心主张**（初稿主推的自动化结构信号被实证证伪）。
> 修正过程完整保留在 §9，不隐藏。**§9 是本文最有信息量的部分，建议优先读。**

## 1. 评审总体意见

**结论：问题定义准确，第 9 节的强制力取舍是全稿最好的部分，建议原样保留。主要问题有两处——债务闭环缺少驱动力（§1.3），以及对现有实践的描述有失公允（§1.2）。**

### 1.1 确认为准确的部分（已实核）

对照仓库实际状态核实，讨论稿第 4 节的缺口判断基本属实：

| 讨论稿的声称 | 核实结果 |
|---|---|
| "没有项目级 tech-debt 或架构债登记规范" | 属实。全仓 grep，协议内容里"技术债"只出现在 `assets/review-roles/plan-eng-review.md:19` 一句评审提示，无模板、无字段规范、无脚本 |
| "agate 自身有 hardening-roadmap，使用 agate 的项目没有同等标准" | 属实。`docs/hardening-roadmap.md`（415 行）是 agate 自用的演进视图，未沉淀成给下游项目的规范 |
| "没有债务条目 → 独立任务 → 关闭验证的标准链路" | 属实。现有 DEVIATION/BLOCKER/SUGGEST/SCOPE+ 全部是**任务内**闭环（`check-scope-resolved.sh` 强制 SCOPE+ 必须在本任务 P1 有 SCOPE_RESOLVED），无"移出本任务、进入项目级"的通道 |

### 1.2 但对现有实践的描述不公允（自评发现，初稿也犯了同样的错）

讨论稿把现状描述为几乎空白。实际上 **`docs/reviews/T001-retrospective-2026-08-10.md` 已经是一份相当成熟的债务捕获实践**：按「技术原因 / 管理原因 / 协议自身原因」三类分表，每条有编号（T1-T4 / M1-M5 / A1-A6）、根因、影响，并且在结论里明确点出"3 个技术债问题全部是旧机制+新结构化数据结合处的边界情况"。

这不是空白，是**有捕获、无跟踪**：复盘把债写下来了，但没有 id、没有状态、没有关闭条件、没有人回头看。

**这个区分对方案设计有实质影响**：要做的不是"从零建立债务发现能力"（那已经有了，而且质量不错），而是"给已有的发现装上跟踪和关闭"。工作量和风险都比讨论稿隐含的小，且应当**复用复盘的既有分类**（技术/管理/协议），而不是另起一套 `type` 枚举。

### 1.3 核心问题：债务闭环缺少驱动力

讨论稿的数据流是 `review → 债务条目 → backlog → 独立重构任务 → P0-P8 → 关闭`。其中 `backlog → 独立重构任务` 这一步，全文唯一的强制是第 9 节的"高优先级债务在任务看板中可见"。

**"可见"不是驱动力。**这与讨论稿第 3.1 节自己引用的前提直接冲突——agate 整个 hardening-roadmap 建立在"主 Agent 默认倾向于少走路，所有依赖自觉的环节都是脆弱的"这一反复验证的判断上。只靠"可见"驱动的 backlog，恰恰是最典型的依赖自觉环节。

第 11.1 节点名了"债务清单变成垃圾场"，但未给对策。**这是必须补强的第一处。**

外部经验佐证这不是理论担忧：<cite index="12-2">一项覆盖 15 家大型组织、226 名受访者的调查发现，管理技术债占用了平均 25% 的开发时间，但成体系的极少——只有 26% 使用工具，仅 7.2% 有方法地追踪</cite>。<cite index="11-1">技术债项目失败的典型原因不是低估了债务规模，而是清单存在于一个月内就过期的表格里，没人说得清情况在变好还是变坏</cite>。

### 1.4 本仓库内部就有一个完整的失败样本

**这是全文最有说服力的证据，且完全来自本仓库，不需要外部类比：**

1. **2026-08-04**（commit `2ca6f8e`），`--fix` 分支引入总结行归一化的 `[:：]` sed，其中埋下一个 locale 依赖缺陷（在非 UTF-8 locale 下静默失效）——当时无人察觉
2. **2026-08-10**，T001 复盘把 `check-p6-format.sh --fix` 列为技术债 T2，定性为"旧脚本 + 新数据结构耦合面缺少防护"，它是该任务**唯一一次触发正式 P6→P4 回退**的真 bug。修复（commit `afe758a`）**改动的正是同一个 `--fix` 分支**
3. 该债务被写进复盘表格后，**没有 id、没有状态、没有关闭条件、没有后续跟踪**
4. **2026-08-12**，我在对 v0.40.2 做独立状态核实时，在**同一个脚本、同一个 `--fix` 分支**发现了第 1 条那个缺陷（详见 `docs/reviews/review-20260812-0339.md`）

**需要精确说明**：这个 locale bug **不是** T2 修复引入的回归，它自 2026-08-04 起就潜伏在那里，是一个独立缺陷。

**但这恰恰让论证更强，而不是更弱**：08-10 的定向修复**打开的就是同一段 `--fix` 代码**，却没有注意到紧邻的这个潜伏缺陷。原因不难理解——修复是围绕"这一次回退的具体症状"展开的，范围就是那一个 bug。

如果 T2 当时是一条有 `evidence`、有关闭条件、范围写成"`--fix` 分支整体缺乏防护"的 DEBT 条目，关闭它就需要回答"这个分支还有没有同类问题"，那么相邻的 locale 缺陷有相当机会在那一轮被一并发现。**"债务条目"与"缺陷修复"的差别正在这里：后者的范围是症状，前者的范围是区域。**

一个被正确识别、正确定性、但没有被跟踪到关闭的债务点，其所在区域在两天后又暴露出一个已潜伏 8 天的缺陷。**讨论稿要解决的问题，在本仓库已经以完整形态发生过一次了。**

## 2. 需要补强的其他几处

### 2.1 "技术债 vs 普通缺陷"缺少判据

讨论稿第 4.2 节把"没有统一分类"列为缺口，但第 7 节的字段模板（`type: architecture`）只提供了分类的**格子**，没提供**判据**。边界模糊会双向滥用：什么都往 DEBT 扔以逃避当前任务修复；或什么都在当前任务死磕不敢登记。

建议判据见 §5.3，核心是一句可机械问答的话：**"不修它，当前任务的验收声明会不会变成假的？"**

外部实践对这条线的划法一致：用户可见的错误行为是 bug，仍能工作但让后续开发更难更险的内部质量问题是技术债，两者要分开跟踪，因为优先级判据和排期方式不同。

### 2.2 状态机（第 7.2 节）过度设计

`open → accepted → planned → in_progress → resolved → verified → closed` 七态 + 三终止态。对比：`.state.yaml` 的 P0-P8 状态数相当，但那是**任务级、有 gate 强制流转**的。DEBT 条目是**项目级、无 gate 绑定**的自由文本状态——无强制流转的复杂状态机会僵死在前两态（`planned` 永远是 `planned`）。建议三态，见 §5.2。

### 2.3 第 12 节讨论问题的优先级排错

问题 1（存储格式）最不重要；分类判据和问题 4（重构 task type）才是要害。§7 逐条回答并重排。

## 4. 机制设计的关键选择

### 4.1 债务的两个来源，一强制一自愿

| | **回退/gate 失败触发**（强制） | **评审/复盘发现**（自愿） |
|---|---|---|
| 触发条件 | 发生 `retreat:` 提交或正式回退 | 评审者主观判断 |
| 是否必须建条目 | **是** | 否 |
| 精度 | 高（见 §4.2） | 取决于评审者 |
| 覆盖面 | 窄（只覆盖已爆雷的） | 宽 |

**核心设计：唯一的新增硬强制，只加在"已经爆过雷"的地方。**这是本文认为唯一站得住的强制点——它不需要任何人做价值判断（回退是客观事实），不产生形式主义空间，且登记成本极低（回退诊断文字可直接复用）。

它站得住的理由**不是**"实测精度高"（样本仅 1 起，见 §4.2），而是**逻辑上不可能误报**：回退是协议定义的客观事件，已发生的回退必然意味着某处出了真问题。这与需要统计验证的排名类指标性质不同。

### 4.2 为什么是"回退事件"而不是"热点指标"（含一次失败的实测）

**初稿主张用 churn × LOC 热点指标作为主要自动化信号。自评时我用本仓库唯一可得的 ground truth 做了检验，结果是证伪的：**

已知事实：`check-p6-format.sh` 是近期 agate 最"产缺陷"的文件（复盘定性为技术债 T2 + 唯一一次正式回退 + 两天后又发现独立 bug）。

那么各信号能不能把它排到前面？实测（**全仓库历史：首次提交 2026-06-16 至今约 2 个月，661 commits**）：

| 信号 | `check-p6-format.sh` 的排名 | 判定 |
|---|---|---|
| churn × LOC 热点 | **第 96 名**（churn=6, loc=102, score=612） | ❌ 完全漏掉 |
| fix commit 触及次数 | 未进前 12 | ❌ 漏掉 |
| fix 占比（fix/total，≥4 次改动） | 第 22 / 98 名（0.50） | ⚠️ 偏高但不显著 |
| **`retreat:` 提交记录** | **第 1 名（全history 仅 2 条 retreat，均指向它）** | ✅ 精确命中 |

热点指标失效的原因很清楚：它偏向**又大又常改**的文件，而 `check-p6-format.sh` 只有 102 行、6 次改动——**小而刁钻的文件是它的结构性盲区**，而这类文件恰恰容易藏 bug。

回退事件为什么好：agate 协议**已经强制**回退必须写成 `retreat: PX -> PY（诊断：...）` 格式的提交并经人工批准，诊断文字里直接点名了问题组件。这是通用工具没有、而 agate 天生具备的高精度信号，且**零新增埋点**。

实测提取（全仓库历史）：
```
023b28b|2026-08-10|retreat: P5 -> P4（诊断：BDD-17: check-p6-format.sh --fix 破坏 frontmatter...）
29301ad|2026-08-10|retreat: P6 -> P5（诊断：BDD-17: check-p6-format.sh --fix 破坏 frontmatter...）
```

**必须诚实说明的代价**：这个信号**极稀疏**——全仓库历史（661 commits / 约 2 个月）只有 2 条，且属同一起事件。**样本量为 1 起事件，"精度 100%"这个说法在统计上几乎没有意义**，它只说明"没有反例"，不足以支撑"这个信号可靠"的结论。

它是高精度、低召回的**触发器**，不是排名工具。它只能保证"爆过雷的地方一定被登记"，完全无法发现"还没爆雷但正在腐烂"的地方。后者本文没有可靠的自动化答案（见 §8.3）。

### 4.3 为什么绑 P8 而不是新增阶段

讨论稿第 2.1 节的非目标"不为普通功能任务增加固定阶段"，本文完全认同。

P8 是现成锚点：已是强制阶段、已有 gate、已是 subagent 派发（`phase-cards/P8-release.md` 确认 releaser 产出 `P8-release.md`）、频率天然低（发布级而非任务级）。在 P8 加一次"确认债务清单"动作，不新增阶段、不增加普通任务负担，符合第 3.4 节"周期性审视"原则。

## 5. 具体规范

### 5.1 债务条目格式

```yaml
id: DEBT0001
category: technical        # technical|management|protocol  ← 复用 T001 复盘的三分法
title: "check-p6-format.sh --fix 对整份文件无差别 sed 归一化"
status: open               # open|in_progress|closed
priority: high             # high|medium|low
evidence:                  # 必填，必须是可核验的事实
  - path: agate/scripts/check-p6-format.sh
    note: "--fix 分支 sed 作用于整文件，破坏 frontmatter pass:/fail: 字段"
  - ref: "retreat 023b28b / T001 复盘 T2"
impact: "旧脚本+新数据结构耦合面缺防护；已致 1 次 P6→P4 正式回退"
recommendation: "切分 frontmatter/正文后再归一化"
task_id: null              # 立项后填；非 null 即 in_progress
closure_criteria:
  - "frontmatter 字段不被正文归一化影响"
  - "bats 覆盖该场景"
source: retreat            # retreat|review|retrospective  ← 区分强制来源与自愿来源
created_at: 2026-08-10
```

相对讨论稿：删 `affected_areas`（与 `evidence.path` 重复）；`type` 改为复用复盘三分法的 `category`；新增 `source` 以便统计强制来源与自愿来源的比例（这是 §8.2 止损条件 2 的判据）。

`evidence` 必填是关键——讨论稿第 9 节"不能只写代码不好"这条要求，只有把 `evidence` 设为 schema 必填才真正落地。

### 5.2 三态状态机

```
open ──(立项，填 task_id)──> in_progress ──(关闭条件验证通过)──> closed
  └──> rejected / duplicate / wont-fix（终止，须填理由）
```

`task_id` 本身承载"是否已立项"，不需要 `accepted`/`planned` 独立成态。`resolved`/`verified` 合并进 `closed` 的准入条件：**closed 必须引用关联任务的 P5/P6 证据**。

### 5.3 债 vs 缺陷的判据

> **不修它，当前任务的验收声明会不会变成假的？**

- **会** → 当前任务的缺陷，走现有 DEVIATION/BLOCKER 在本任务修，**不许登记成 DEBT**
- **不会，但会让未来变更更贵/更险** → 登记 DEBT，不扩大当前任务范围
- **不会，且不影响未来变更成本** → **什么都不是，不要登记**

第三条同样重要：第 11.1 节担心的"垃圾场"，一半来自没有"什么都不登记"这个合法出口。

配套硬规则（防止用 DEBT 逃避当前任务）：**若某问题被登记为 DEBT，当前任务的验收声明不得包含依赖该问题已解决的表述**。由 P7 一致性评审人工核对，不需新脚本。

### 5.4 强制力总表

| 环节 | 强制什么 | 不强制什么 |
|---|---|---|
| 发生 `retreat:` 回退 | **必须建 DEBT 条目**（`source: retreat`） | 不强制何时修 |
| review/复盘提债 | 用标准格式、`evidence` 非空 | **不强制每次都提** |
| DEBT → closed | 必须有 `task_id` + P5/P6 证据引用 | 不强制关闭时限 |
| P8 发布 | 必须**看过**清单并留痕（含"本次无关注项"这一合法选项） | **不强制任何指标达标、不阻断发布** |
| 普通任务 | 无新增负担 | — |

## 6. 实施计划（三个必做阶段 + 一个默认不做的可选阶段，每阶段独立止损）

**阶段顺序相对初稿做了对调**——先做人工登记规范，后做（可选的）自动化，理由见 §9。

### Phase 1：DEBT 登记规范 + schema 校验（先做这个）

**产出**：
- `assets/templates/tech-debt-template.md`（下游项目放 `docs/agents/tech-debt.md`）
- `agate-debt-check.py` + `check-debt.sh`：schema 校验（必填字段、枚举、`evidence` 非空、`closed` 必须有 `task_id` 与证据引用）
- review 角色卡（`plan-eng-review.md` 等）追加："如提出后续应重构/存在架构债，须用标准 DEBT 条目格式"

**复用既有机制**：schema 校验沿用 v0.40.0 已落地的 frontmatter 校验模式（`agate-frontmatter-check.py` + fail-closed wrapper），不新造轮子。

**回填验证（关键，且几乎零成本）**：把 T001 复盘已有的 T1-T4 / A5 / A6 直接回填成 DEBT 条目。这些条目现成、已有根因和影响、质量高。**若连这些都填不进模板，说明模板设计错了**——这是一次成本极低的设计验证。

**验收**：T001 复盘的既有条目能无损回填；`evidence` 为空必须被拦；bats 覆盖合法/非法各若干。

### Phase 2：回退事件强制建条目

**产出**：
- `phase-cards/` 回退相关卡片 + `rules/state-transitions.md`：明确"回退落地后必须建 DEBT 条目"
- 轻量脚本：从 `git log` 提取 `retreat:` 提交，与 `tech-debt.md` 中 `source: retreat` 的条目比对，缺失则报 WARNING

**为什么放第二**：它依赖 Phase 1 的条目格式存在。技术上极简单（`git log | grep` 加比对），风险几乎只在规范措辞。

**验收**：用已有的 2 条真实 retreat 记录做 fixture，未建条目时能报出。

### Phase 3：P8 锚定 + 真实闭环验证

**产出**：
- `phase-cards/P8-release.md` 增加一步：确认债务清单，结果写入 `P8-release.md`
- `check-gate.sh` P8 分支增加留痕检查（**只查留痕存在，不查内容达标**）

**验收（这才是整个方案的真验收，前两阶段都只是准备）**：用一个真实重构任务跑通 `DEBT 登记 → 立项 → P0-P8 → 回归 → closed` 完整闭环。

**首个试点建议就用 `check-p6-format.sh`**：它已产出两个缺陷——复盘 T2（frontmatter 破坏，**已在 v0.40.0 修复**）与 locale bug（**尚未修复**，见 `docs/reviews/review-20260812-0339.md`）。边界清楚、体量小（102 行）、且是本文论证链条的起点。

用它闭环的好处是两条路都能走：**未修的 locale bug 可以走完整的"登记→立项→修复→关闭"**，而**已修的 T2 可以直接回填成一条 `closed` 条目**用来检验关闭条件与证据引用格式是否可用——一个试点同时验证了状态机的两端。

**若闭环跑不通，前两阶段产出应视为失败并回退**，而不是留着当"反正没坏处"的死代码。

churn 热点 / 时序耦合 / fix 占比。**默认不做**，理由见 §9 与 §4.2 的实测证伪。仅当 Phase 3 闭环稳定运行、且出现"债务总是等到爆雷才被发现"的实际证据时，才重新评估。

## 7. 对讨论稿第 12 节七个问题的回答（按重要性重排）

**Q3 review 发现债务时格式是否强制？**
→ **强制格式，不强制产出**。可以不提债；一旦提"后续应重构/存在架构债"，必须用标准条目且 `evidence` 非空。不强制格式则出口形同虚设；强制产出则制造形式主义（第 9 节已正确排除）。**例外**：回退事件强制建条目（§4.1），因为那不需要任何价值判断。

**Q4 "重构任务行为不变"是否需要新 task type？**
→ **需要一个字段，不需要新阶段、不需要新模板体系**。`P1-requirements.md` frontmatter 加 `change_type: refactor`，其影响是改变 P6 验收口径（不伪造功能 BDD，改用全量回归 + 关键路径验收）——讨论稿第 8 节已写对，直接采纳。不需要新 task type：重构任务的 P0-P8 骨架与普通任务完全相同，差异只在 P6 口径。

**Q1 债务条目存哪？**
→ **单一 Markdown（`docs/agents/tech-debt.md`），每条目一个 YAML 块 + 正文补充**。与既有 `known-failures-template.md` 形态一致（团队已熟悉）；单文件便于人读全貌；YAML 块保证机器可校验。不用纯 YAML 文件是因为条目需要大段正文说明权衡——讨论稿 §7.1 结尾自己也提醒"不要把所有语义强行压进 YAML"。

**Q5 哪些债必须阻断发布？**
→ **一条都不阻断**。P8 只强制"看过并留痕"。一旦某类债能阻断发布，登记该类债就等于给自己找麻烦，**结果必然是不登记**——这是第 10 节担心的 Goodhart 问题的最短路径。宁可承认"带着已知债发布"，也不要制造"为了发布而不登记"的激励。

**Q6 项目级审视按什么触发？**
→ **按发布（P8）**，理由见 §4.3。任务数量触发需新计数器且阈值难定；人工触发等于没有触发。

**Q2 `tech-debt.md` 够不够，是否必须同时维护架构快照？**
→ **`tech-debt.md` 够，不做架构快照**。与讨论稿结论一致。初稿曾主张"快照改为脚本生成即可救活"，被自评证伪（§9）——生成成本确实低，但生成出来的信号质量不足以支撑决策，低成本的无用信息仍然是无用的。

**Q7 P2.71 作为 v2.1 顶层主题还是小试点？**
→ **先做 Phase 1，不占顶层主题**。等 Phase 3 真实闭环跑通再决定是否升格。这是讨论稿第 13 节自己的"先试后决定"原则，本文只是把它具体化成了可执行的止损点。
（核实：`docs/hardening-roadmap.md` 当前 P2.x 最大编号 P2.69，P2.71 未被占用，无冲突。）

## 8. 风险与止损

### 8.1 风险与对策

| 风险 | 对策 | 残留 |
|---|---|---|
| DEBT 清单变垃圾场 | §5.3 判据含"什么都不是"的合法出口；`evidence` 必填抬高登记成本 | 无法完全杜绝 |
| 用 DEBT 逃避当前任务修复 | §5.3 硬规则 + P7 核对 | 依赖 P7 人工判断 |
| 回退强制建条目退化成敷衍条目 | `evidence` 必填 + 回退诊断文字可直接复用（成本本就极低） | 条目质量仍靠人 |
| P8 确认退化成无脑打勾 | 见 §8.2 止损 4 | **本方案最可能的失败方式** |
| 指标被优化（Goodhart） | 所有指标只做趋势不做 gate；Q5 明确一条都不阻断发布 | 第 10 节已正确识别 |
| **只能发现已爆雷的债** | **无对策**，见 §8.3 第 1 条 | **本方案最大的能力缺口** |

### 8.2 止损条件（缺了这个，任何机制都会变成僵尸）

任一条成立即回退对应阶段，而非继续加码：

1. Phase 1 交付后，T001 复盘既有条目**无法无损回填** → 模板设计错误，重新设计
2. Phase 2 交付后，连续 5 个任务的 review **一条自愿 DEBT 都没提**（`source: review` 为 0，全靠 retreat 强制） → 自愿通道已死，需重新设计而非强制产出
3. Phase 3 交付后，DEBT 条目**无一条走到 closed 且中位存活时间持续增长** → backlog 已成垃圾场，停止登记新债，先清存量
4. P8 的"确认已读"连续 3 次发布都是空确认（无关注项、无后续动作） → 该强制已退化为形式主义，**移除它**

外部数据可作为止损 3 的基线参照：<cite index="22-1">开源项目中自承认技术债的中位存活时间在 18 到 172 天区间</cite>，且<cite index="27-1">其中 20% 到 50% 是被顺手误删的，只有约 8% 的清除动作会写进 commit message</cite>——"债被记下来但没人有意识地还"是常态而非例外。

### 8.3 未解决 / 不确定（诚实标注）

1. **本方案只能可靠发现"已经爆雷"的债**。回退事件召回极低（全仓库仅 2 条）；自愿通道的召回取决于评审者。"还没爆雷但正在腐烂"的地方，本文**没有可靠的自动化答案**——初稿以为热点指标是答案，实测证伪（§9）。这是真实的能力缺口，不应粉饰。
2. **观察窗口太短，所有频率类结论都不稳**。agate 仓库首次提交 2026-06-16，至今约 2 个月（661 commits）。"2 条回退"既可能是真实的低频，也可能只是窗口太短——**无法区分**。下游项目回退频率可能完全不同（更高则信号更有用，更低则近乎无信号）。Phase 2 的价值高度依赖这个未知数，这是本方案最不确定的经验前提。
3. **三态状态机是否够用没有实证**，只有"七态会僵死"的推理。若 Phase 3 发现确需区分"已立项未开工"与"开工中"，应加回一态，不必固守三态。
4. **`category` 复用复盘三分法（技术/管理/协议）未经检验**是否适合下游项目——"管理原因"对单人项目可能无意义。
5. 本文引用的窗口（"近 3 个月""近 6 个月"）实际都覆盖了仓库全history（仓库仅约 2 个月），因此**未做也无法做窗口敏感性分析**；所有原型跑在 agate 自身（Markdown 为主的仓库）上，对典型代码项目是外推。

## 9. 自我评审记录（初稿被推翻的过程）

按 agate 既有纪律，self-authored 文档存在 producer=judge 结构性局限，故此处完整记录自评发现，不隐藏修正痕迹。

**初稿的核心主张**：讨论稿否决方案 C（架构健康快照）的理由是"维护成本高、会过期"，而这只在"人手写快照"前提下成立；改为**脚本从 git 生成**后成本坍塌，因此应采用"方案 B+"——B 加上自动生成的结构信号（churn×LOC 热点 + 时序耦合）。初稿还据此把"结构信号脚本"排为 Phase 1。

**自评做了什么**：初稿已经用原型在本仓库跑出了热点榜和耦合榜，看起来"信号有意义"（`dispatch-protocol.md`、`check-gate.sh` 高居前列，与我此前对 agate 复杂度增长的独立观察吻合）。但这是**确认偏误**——我只检查了"输出看起来合理"，没有检查"它能不能命中已知的正确答案"。

于是我找了本仓库唯一可得的 ground truth：`check-p6-format.sh`（复盘定性技术债 + 唯一正式回退 + 同一分支另有潜伏缺陷）。结果见 §4.2 的表——**热点指标把它排在第 96 名，完全漏掉**。

**为什么会漏**：热点指标偏向"又大又常改"，而这个文件只有 102 行、6 次改动。**小而刁钻的文件是 churn×LOC 的结构性盲区**，而这类文件恰恰容易藏 bug。

**由此产生的三处实质修改**：

1. **推翻 B+，回到 B**（与讨论稿原结论一致）。低成本的无用信息仍然是无用的——"生成快照"解决了成本问题，但没解决**信号质量**问题，而我初稿只论证了前者。
2. **换主信号**：改用 `retreat:` 回退事件——全仓库 2 条回退均指向该文件，零新增埋点（协议本就强制回退写标准格式提交），且不需要任何人做价值判断。这是 agate 相对通用工具的**结构性优势**：协议强制记录了通用工具拿不到的东西。（注：样本仅 1 起事件，其可靠性依据是"逻辑上不可能误报"而非统计验证，见 §4.1。）
3. **调换阶段顺序**：初稿 Phase 1 是结构信号脚本，现改为 DEBT 登记规范；结构信号降为可选的 Phase 4 且默认不做。

**同时发现的第二个错误**：初稿沿用了讨论稿"现状接近空白"的框定，忽略了 T001 复盘已是成熟的债务捕获实践（§1.2）。修正后方案改为**复用复盘的三分法分类 + 回填复盘既有条目做验证**，工作量和风险都下降。

**这次自评的一般教训**（值得记进协议）：**"原型跑出来的结果看起来合理"不等于"机制有效"。**必须找一个独立已知的正确答案去检验命中率。初稿两次实测（热点榜、耦合榜）都只是在确认输出可读，没有一次是可证伪的检验——这正是 LIMITATIONS 局限 3「能满足的任何 bar 都不可信」在**方案设计阶段**的翻版：我自己设计的指标，自己看输出觉得合理，这个 bar 是我自己能满足的，因而不可信。

## 10. 一句话总结

讨论稿把问题定义对了、把不该强制的东西正确排除了，且**它对方案 C 的否决是对的**（本文初稿曾试图推翻，自评后收回）。

本文的实质贡献有三点：指出**"债能进 backlog"与"债会被处理"之间缺驱动力**；给出一个**唯一新增硬强制**（回退事件必须建条目——客观事实触发，逻辑上不可能误报，无价值判断空间）；以及用**本仓库自己的失败样本**（`check-p6-format.sh`：识别为债 → 未跟踪 → 两天后在同一分支查出已潜伏 8 天的缺陷）证明这不是假想问题。

建议下一步：只做 Phase 1，并用回填 T001 复盘既有条目来验证模板——成本极低，且能立刻暴露模板设计是否可用。
