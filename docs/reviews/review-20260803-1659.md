## 3. 独立发现：审计 6（P2.57）可被同脚本内更早的 agent 字段检查静默短路

这是本次评审最重要的发现，两份仓库自带的 alignment review 均未捕获。**强调一次：此问题与 agent 是否主动造假无关，是纯粹的代码执行顺序问题。**

### 3.1 问题机制：为什么"不阻塞"的检查会挡住后面的硬拦截

`check-p6-provenance.sh` 是一份从上到下顺序执行的 bash 脚本，依次做：审计1（证据-结论对应）→ 审计2（dispatch-context约束）→ 审计3（BDD总数对照）→ 审计4（UI vision YAML）→ 审计5（EXIT_CODE一致性）→ **agent 字段检查（协作规范）** → **审计6（evidence JSON 一致性，L256-304，本次 P2.57 新增，专门修 T084 那种"commit 声称全 PASS 但 evidence 有 FAIL"的问题）**。

问题出在 agent 字段检查这一段（L228-253）的实现方式：

```bash
if [ -z "$AGENT" ]; then
    echo "GATE PROVENANCE: ... 缺 agent 字段（协作规范，不阻塞）" >&2
    exit 2
fi
```

`exit 2` 在 bash 里不是"记一笔警告然后继续往下走"，而是**整个脚本进程立即终止**——和函数的 `return` 是两回事，`exit` 是把整个脚本杀掉，它后面的所有代码（包括审计 6）都不会再执行。

也就是说，"协作规范，不阻塞"这句话描述的是**这条规则本身的严重程度**（它认为"缺 agent 字段"不该导致 gate 失败），但代码层面选用的实现手段（`exit 2` 终止进程）产生的实际效果是"**这条检查一旦触发，会把它后面所有的检查都一起带走**"——这两者的语义完全对不上：规则设计者认为的"不阻塞"，在执行层面变成了"阻断了所有下游检查"。

打个比方：这就像安检流程里"检查工牌"这一关，没戴工牌本该只是"记录一下，提醒一句"，但代码实现却写成了"没戴？没事——直接放你出安检口"，导致后面真正的金属探测器（审计 6）根本没机会检查。

### 3.2 触发条件：不需要任何造假意图

触发条件只是：任务目录里**任意一个**阶段产出文件（P1-requirements.md、P2-design.md、P4-implementation.md 等，代码用 `$TASK_DIR/P[0-8]-*.md` 通配符扫描全部）缺少 `agent:` frontmatter 字段。这可能来自：

- 使用了协议自己承认的"v2 之前创建的旧格式文件"（代码注释原文：`向后兼容：v2 之前创建的文件无 agent 字段，降级为 WARNING 不阻塞`——这明确是被设计为应当继续正常工作的场景，不是异常输入）
- 主 Agent 或 subagent 单纯漏填了一个 frontmatter 字段
- 任何跟"是否伪造证据"完全无关的疏漏

换句话说，**即使这次任务里主 Agent 完全诚实地在走流程、没有任何造假动机，只要某个文件漏了一个字段，审计 6 照样会被跳过**。这是本次发现的核心：它不是"agent 想办法绕过检测"，而是"检测机制自己在正常、无恶意的输入下就失灵了"。

### 3.3 复现

用最小化的合法任务目录结构手工构造 fixture（P1-requirements.md 含 2 条 BDD 标题、P6-acceptance.md 声明 BDD-2 为 PASS 且正确引用了证据文件、P6-evidence/bdd-results.json 客观记录 BDD-2 为 fail），直接调用 `agate/scripts/check-p6-provenance.sh`（脱离 bats 测试框架的真实执行）：

- **P1-requirements.md 缺 `agent:` 字段时**：脚本在 agent 字段检查处触发 WARNING 并 `exit 2`，**审计 6 完全没有执行**，BDD-2 的 PASS/FAIL 矛盾没有被发现，输出里也没有任何字样提及"证据一致性未检查"。
- **补上 `agent:` 字段后重跑同一份 fixture**：审计 6 正常触发，`exit 1`，精确报出"BDD-2: P6 标 PASS 但 evidence JSON 显示 FAIL"。

两次唯一的变量就是有没有 `agent:` 字段，结果从"完全没检测到问题"变成"精确抓住问题"——证明审计 6 本身的判定逻辑是对的，纯粹是执行顺序把它挡住了。

### 3.4 为什么现有的 519 个测试没有发现

`check-p6-provenance.bats` 中审计 6 的全部四个测试（PV.24/25/26/27）在构造 fixture 时都显式写了 `agent: test`（如 PV.24 的 `P6-acceptance.md` frontmatter），这意味着这四个测试从未真正触碰到 agent 字段检查这条短路路径。同时 PV.14（"P6 缺 agent 字段 期望 exit 2"）验证的是 agent 字段检查本身，但它的 fixture 里没有同时构造"evidence 与 acceptance 矛盾"的场景，所以也没有暴露两者组合时的短路问题。

**两组测试各自独立通过，但它们的交集——现实中最可能出现的"旧任务目录/漏填字段 + evidence 矛盾"组合——完全没有测试覆盖**，519/519 全绿的数字因此没有反映出这个 gap。

### 3.5 影响评估

- **触发门槛很低**：不需要恶意，一个疏漏的 frontmatter 字段就够了；代码注释还明确说这是要继续支持的正常场景，不是边缘 case。
- **静默程度高**：exit 2 的输出文案是"协作规范，不阻塞"，完全没有提示"审计 6 因此未执行"，排查者几乎不可能从输出反推出这一点。
- **正好命中 P2.57 本身想堵住的那类问题**：T084 的 P6 commit 声称 14/14 PASS 但 evidence 是 8/10，这正是审计 6 要拦截的场景。如果那次任务恰好有个文件缺 `agent:` 字段，同款问题会在审计 6 已经存在的情况下，一次都不会真正生效，只是这次触发短路的原因和"agent 造假"无关，纯属巧合的字段缺失。

### 3.6 建议修复方向（任选其一）

1. **把 agent 字段检查挪到审计 6 之后**，作为脚本执行的最后一步（"协作规范、不阻塞"的性质不变，只是调整执行顺序，不改变它自身的判定逻辑）。
2. **agent 字段检查不再用 `exit 2` 立即终止，而是把 WARNING 记到一个变量里，继续往下执行完审计 6（以及脚本里剩余的所有检查），最后统一判断：如果有任何审计触发了 `exit 1` 级别的问题就 `exit 1`；否则如果记录过 WARNING 就 `exit 2`；都没有则 `exit 0`。** 这是更彻底的修法，能避免未来任何新增的检查都被这条分支意外挡住。

无论选哪种，都建议新增一条 bats 测试（可命名为 PV.28）：**"agent 字段缺失 + evidence/acceptance 矛盾同时存在 → 仍应 exit 1（审计 6 不应被 agent 字段检查短路）"**，把这个交集场景显式钉死，防止未来回归。
