## BLOCKING：`check-p6-format.sh --fix` 在 POSIX/C locale 下对全角冒号总结行静默失效

### 复现

```bash
unset LC_ALL LANG   # 容器默认 locale，LC_CTYPE=POSIX
cat > P6-acceptance.md <<'EOF'
- PASS BDD-1: verified (evidence/log.json)
- PASS：34
- FAIL：0
EOF
bash scripts/check-p6-format.sh --fix P6-acceptance.md
echo "EXIT:$?"   # → 0（声称成功）
cat P6-acceptance.md   # → 文件内容完全未变
```

`--fix` 报 `exit 0`（成功），但全角冒号的两行总结行（`- PASS：34` / `- FAIL：0`）完全没有被归一化成 `**Summary**: PASS: 34` / `**Summary**: FAIL: 0`。

### 根因（逐层剥离到字节级确认）

`scripts/check-p6-format.sh` 第 82 行：

```bash
FIXED=$(printf '%s' "$FIXED" | sed -E 's/^-\s+(PASS|FAIL)\s*[:：]\s*([0-9]+)\s*$/\*\*Summary\*\*: \1: \2/')
```

`[:：]` 这个 bracket expression 里混入了半角 `:` 和全角 `：`（3 字节 UTF-8：`ef bc 9a`）。POSIX bracket expression 语法里 `[:` 开头会被 sed 尝试解析成 POSIX character class token（如 `[:alpha:]`）的起始——在 **`LC_CTYPE=POSIX`（单字节 locale）下**，sed 对多字节 UTF-8 字符的 bracket-expression 处理退化，导致这个 class 无法正确匹配全角冒号，整条 pattern 匹配失败，`sed` 视为无替换发生，`$FIXED` 与 `$BODY_PART` 逐字节相同 → `CHANGES` 判定为 0 → 文件不写回。

用最小对照实验隔离验证：

```bash
# 单独控制变量：只切换 locale，其余完全相同
unset LC_ALL LANG; locale | grep LC_CTYPE   # POSIX
printf '%s' "- FAIL：0" | sed -E 's/[:：]/X/'   # 结果：不匹配，原样输出

export LC_ALL=C.UTF-8; locale | grep LC_CTYPE   # C.UTF-8
printf '%s' "- FAIL：0" | sed -E 's/[:：]/X/'   # 结果：正确替换为 X
```

**范围界定（避免过度归因）**：

- 只影响第 82 行（总结行归一化正则，`\s*[:：]\s*` 要求全角冒号在 pattern 中段被消费匹配）
- 第 69 行同样含 `[:：]`，但那里全角冒号只是"行首 pass/fail 后跟随分隔符"这个 alternation 的其中一支，其余分支（如 `$` 结尾锚定）仍可命中，实测该行在 POSIX locale 下**不受影响**（单独验证过，见下方"未受影响路径"）
- `--check` 模式（第 33-44 行）完全不使用 `[:：]`，只用 ASCII `[[:space:]]` 和 `\b`，能正确检测出全角总结行是格式偏差——**检测本身没问题，只有 `--fix` 的自动修复这条路在此 locale 下失效**
- GitHub Actions `ubuntu-latest` 默认 `LANG=C.UTF-8`，CI 环境不会暴露此问题，这解释了为什么这个 bug 能一路带到 v0.40.2 未被抓到

**未受影响路径验证**：

```bash
unset LC_ALL LANG
printf '%s' "pass：34" | sed -E 's/^([[:space:]]*)(pass)([[:space:]:：]|$)/\1- PASS\3/'
# → "- PASS：34"（正确匹配替换，第69行这条路径在POSIX locale下工作正常）
```

### 实际影响

不是数据损坏或误放行类的高危问题——`--check` 仍会正确拦截全角总结行格式偏差。影响面是：**在 `LC_CTYPE` 非 UTF-8 的 shell 环境里（部分精简 Docker 镜像、部分未显式配置 locale 的开发机），用户跑 `--fix` 会得到"exit 0 成功但文件没变"的假象，然后 `--check` 依旧拦截，陷入"修复报成功但修复不生效"的困惑循环**。CI 因为默认 UTF-8 locale 不会触发，属于纯本地环境依赖的问题。

### 建议修复方向

三选一，都能规避 POSIX-locale 下 bracket expression 对多字节字符的处理问题：

1. 把 `[:：]` 换成非 bracket-expression 写法：`(:|：)`（alternation 而非字符类，不触发 POSIX class token 解析歧义）
2. 在脚本开头显式 `export LC_ALL=C.UTF-8`（若该 locale 在目标环境不保证存在，需要 fallback 判断）
3. 用 `grep -P`/`perl` 替代该处 sed（PCRE 对 UTF-8 的处理不依赖 bracket-expression 的 POSIX class 歧义），但会新增 perl 依赖，与协议"纯 bash/sed/grep 零额外运行时依赖"的定位冲突，不推荐

个人倾向方案 1，改动最小、不引入新依赖、不依赖环境变量传递。

### 建议追加测试

现有 F12/F_P6FMFIX.2 已经能在本容器复现失败，说明测试用例本身没问题——**这不是"缺测试"，是环境（CI 默认 UTF-8 locale）掩盖了一个真实存在于其他 locale 下的行为分支**。建议追加一条显式设置 `LC_ALL=POSIX`（或 `LC_ALL=C`）运行 `--fix` 的用例，把这个 locale 依赖钉死在测试矩阵里，防止修复后又在某次重构里回归。
