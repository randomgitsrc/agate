## B1（BLOCKER）：实测案例分析未核实是否为既有机制执行缺口

§1.4 举证 TPV0095 backend 批次"横跨 9 个文件+2 个新模块+37 条红灯测试"，据此论证"批次粒度问题只有执行中才浮现，主 Agent 无法在派发前预判"。

但按 `dispatch-protocol.md` §1 工作量评估五维评级：

- 产出规模：9 个文件（含 2 新模块）→ 超过"4-6 个文件"的 medium 上限，落入 high 档（>6 个文件）
- 耦合度：新模块 team_service.py + api/teams.py 需要与 entry_service.py / star_service.py / share_service.py 三个既有服务耦合改造 → 至少"与 ≥3 个模块耦合"，同样落入 high 档
- 改动性质：新增 API 路由 + 既有服务收敛改造 + CLI 命令新增 → 符合"跨模块改动、接口变更"，high 档

按现有规则，**该批次任一维度 high 即整体 high，必须拆分（模式 2/3/4/5 之一）**，且这个评级理应发生在 **P2 阶段**（dispatch-protocol.md 全阶段适用表："P2 | 模式 1（单发）+ dispatch_plan: 产出 | 非 P2 自身拆分——P2 评估并声明后续阶段的编排方案"）。

文档 §1.4 承认"改动表是 P2 阶段的产出"，却没有进一步追问：**这次案例里，P2 阶段的 dispatch_plan 是否正确评估出了 high 并声明了拆分方案？如果声明了但主 Agent 派发 P4 时未遵照执行，这是执行纪律问题，不是本设计要解决的"结构上不可预判"问题；如果 P2 确实评估遗漏（评级本身错误），这是既有五维评级机制的准确性缺口，同样不是本设计的范畴（本设计的边界是"给 subagent 装自主再派发能力"，不是"修正 P2 评级"）。**

只有在"P2 已经正确评估为 high 且已声明拆分方案，但由于该批次内部的可拆分性在字面粒度上无法用静态五维评级捕捉（比如四段之间存在隐性依赖，只有 executor 读懂 P2-design 细节后才能定顺序）"这种情况下，本设计的论证才成立。当前文档没有做这层区分，存在把"既有机制执行不到位"包装成"新问题需要新机制解决"的风险，会削弱设计动机的说服力，也可能导致评审通过后发现真正该修的是 P2 评级执行纪律而非新增子派发能力。

**修复建议**：核实该实测案例 P2-design.md 是否声明了 dispatch_plan 及具体评级结果；若评级本身是 high 但未拆分执行，需在 §1.4 补充说明"本设计不替代既有五维评级的正确执行，仅补充评级已经做对、但批次内部依赖关系需要执行中动态判断"这一更精确的问题边界；若发现评级确实遗漏，应单独登记为独立的技术债（既有机制缺口），不与本设计混同。

## B2（BLOCKER）：子任务心跳文件的落盘归属未定义

§3.3 提到"父 subagent 是否给自己的子任务也包一层心跳，是它自己的执行细节，对主 Agent 完全透明"，但心跳文件本身是要落盘到文件系统的（§3.2 示例路径 `${TASK_DIR}/.heartbeat`），"透明"不等于"不存在于文件系统"。

需要明确：

1. 子任务心跳文件如果也落在 `${TASK_DIR}/` 下（沿用父任务同一目录），是否会与父任务自己的 `.heartbeat` 文件冲突（同名覆盖）？
2. 若不冲突（比如子任务用独立子目录），这些文件是否会被现有的 provenance 审计（`check-p6-provenance.py`）或一致性扫描（`check-protocol-consistency.py`）意外扫描到，产生噪音或误报？
3. 任务结束（父 subagent 返回后）这些心跳文件是否需要清理，避免任务目录堆积大量 `.heartbeat` 类文件影响后续审计的文件枚举效率？

这不是可以留给"执行细节"一句带过的问题——一旦心跳机制本身要落盘到 `agate-workspace/tasks/` 目录下，就进入了协议管辖的文件系统命名空间，需要有明确的命名规范和生命周期定义，否则会在真正实现时产生歧义或与既有审计脚本冲突。

**修复建议**：补充一节明确心跳文件的完整生命周期——命名规范（建议父子分层命名，如 `.heartbeat` vs `.heartbeat.child-{n}`）、是否纳入既有 `.gitignore`/审计豁免规则、任务完成后的清理时机（可比照 `agate-archive-stale-outputs.py` 的既有归档收尾模式）。
