## 三、复盘分析

### 技术原因

| # | 问题 | 根因 | 影响 |
|---|---|---|---|
| T1 | `agate-frontmatter-check.py` 异常处理不完备 | 只捕获 `yaml.YAMLError`，未对 `main()` 主逻辑做兜底 try/except，`RecursionError`/`UnicodeDecodeError` 等未预见异常会穿透 | CRITICAL：坏格式文件被静默放行（fail-open），若未被 C8 review 拦下会成为发布缺陷 |
| T2 | `check-p6-format.sh --fix` 对整份文件做无差别 sed 归一化 | 该脚本本身早于 T001 存在，设计时 frontmatter 字段少且简单，未预料到会有结构化 `pass:`/`fail:` 字段需要保护；T001 新增这些字段后才第一次触发 | BDD-17：唯一一次触发正式 P6→P4 回退的真 bug，是"旧脚本 + 新数据结构"耦合面缺少防护的技术债 |
| T3 | 任务编号格式硬切（流 D）对下游隐性依赖面估计不足 | 测试脚手架大量用旧格式 `task_id`（如 `T001`/`T999`）做占位符，硬切正则后被 pre-commit hook 拦截 | 33 个既有测试回归，需要额外一轮定向修复（非设计缺陷，但暴露"全局约束变更"影响范围排查不彻底） |
| T4 | bash 工具在当前环境下多次挂起/超时 | 环境工具链稳定性问题，非改造本身缺陷 | 拖慢执行节奏（P2→P3 之间 3.5h gap 与此时间上重合），最终被固化为 9 条 AGENTS.md 工具纪律规则，属于用一次事故换来一份可复用的流程资产 |

### agate 协议自身原因（本次改造对协议设计的验证/暴露）

| # | 现象 | 分析 |
|---|---|---|
| A1 | **retreat 机制第一次在大任务里被完整走通** | P6→P5→P4 的正式回退（diff=2，需人工批准，走 `P6-gate-diagnosis.md` + `PAUSED-resolution.md` + `[HUMAN_CONFIRMED:]` 全套流程）证明状态机回退设计可用，不是纸面流程 |
| A2 | **self-gate + DESIGN_GAP 机制的价值被真实验证** | C8 review 拦下 1 个 CRITICAL、self-gate 拦下多处文档滞后 MISALIGNED、终审又拦下 3 处遗留问题——这些都是协议设计初衷要拦的东西，且真的拦住了，不是走过场 |
| A3 | **但 self-gate 机制本身不是一次到位的** | 初版 `protocol-alignment-review.md` 缺少对"已知可接受偏离（DESIGN_GAP）"的处理原则，会有把已知偏离误判为新 MISALIGNED 的风险；升级后自己又留了 2 处内部表述矛盾（"DESIGN_GAP 覆盖项算不算 MISALIGNED"三处文本不一致）。说明**审查者角色定义本身也是活文档，需要用真实运行数据反复迭代**，不能假设一次写对就永久有效 |
| A4 | **自举（dogfooding）暴露了双工作区模式的固有代价** | 真正生效的 git hook 共享同一份 `~/.agate`（v0.35 未修复版），导致 T001 自己的 P6-acceptance.md 被迫舍弃刚设计出来的 `pass:`/`fail:` 结构化字段（否则会被旧版 `--fix` 破坏）。这是"用旧协议改造协议自己"这种自举模式下无法避免的结构性限制：**协议在被改的过程中，无法用半成品的自己来验证自己，只能继续用旧版本兜底** |
| A5 | **P0 阶段缺少强制的"关键数字核对"检查** | M1 的两处数字错误本可以被一个轻量的"运行脚本回填校验"步骤拦住，而不必等到 P1 开始后才发现——这是协议流程上一个可以补的轻量 gate，成本低、收益明确 |
| A6 | **协议只管"任务内"的质量，管不到"任务外"的信任建立** | P0-P8 状态机把"验收通过"和"用户认可可以合并"当成同一件事，但 M5 的实测数据（连续两次拒答合并问题）说明用户对"能否安全合并进 main、影响本机所有项目"这件事的信任阈值，比协议自身的 gate 标准更高。这不是协议缺陷，而是提示：**涉及"影响范围外溢"（这次是 `~/.agate` 全局生效）的发布动作，或许值得在 P8/READY 之外单独建模为一道更高阈值的确认**，而不是默认 READY = 可以合并 |

## 四、结论
