## B1'（BLOCKER）：条目"PASS"标签与随附评审证据矛盾

条目摘要写"独立评审 PASS"，但条目内可查的**唯一**评审文件结论是"FAIL（需迭代）"，且该评审核验的具体措辞（4.1 的"并行批/流水线/独立复核/跨轮续跑"）是 v2 文档自己承认已经改掉的旧版本内容。也就是说：

```text
时间线复原：
  v1 文档撰写 → 独立评审（2026-09-01）→ 结论 FAIL（B1+B2+4W+4N）
  → 提交者按评审意见修订出 v2（本次审查对象）
  → 条目摘要标注"独立评审 PASS"
  → 但条目里没有第二份评审文件证明"谁、在什么时候、针对 v2 的具体修改点"做过复核
```

这不是"评审意见没有被认真对待"的问题——相反，从内容核验看，v2 对 B1/B2/W1-4/N1/N3/N4 的修复大多是实质性的、有针对性的（见上表），修订质量本身不差。问题在于**"PASS"这个结论是从哪里来的**：如果是提交者自己判断"我已经按评审意见改完了，所以标 PASS"，这在 Agateon 自己的方法论里恰恰是**self-authored gate** 的典型样例——修改者自己评估自己修改得够不够好，然后自己贴上"独立评审通过"的标签。这与 Agateon 协议本身反复强调的"判定权不能留给被判定者自己"（BDD-9、P6.5 独立 judge、known-violations 三重门槛等机制的设计初衷）直接冲突。

推演其后果：

```text
若"PASS"标签可以在没有第二轮独立评审的情况下自行贴上
→ 任何 v1→v2 的修订，无论修得好坏，提交者都可以同样贴"PASS"
→ "独立评审"这个质量关卡在流程上被绕过，只在文档措辞层面留下"经过评审"的痕迹
→ 这正是 RM-AG0046 v1→v2 那次教训的镜像重演：
  known-violations 机制曾经因为"复刻算法但不复刻背后的道德约束"留了一个漏洞（B3）；
  这里是"复刻'评审通过'这个结论的措辞，但没有复刻'评审通过'背后必须真的有人独立复核"这个约束
```

可选修正：

1. 条目摘要的"PASS"应改为准确状态，例如"v2（针对 v1 评审的 2 BLOCKER+4 WARNING+4 NIT 逐条修订，待独立复审）"；
2. 若确实存在一次真正针对 v2 内容的独立复审，应作为**第三个文件**附在条目里（而不是让读者靠猜测"v2 里写的修订说明"等同于"已经过复审"）；
3. 建议以后类似条目命名约定里区分"自评已修复"和"独立复核已通过"两种状态，避免摘要字段成为唯一但不可靠的状态来源——这与 Agateon 协议里 `known-violations.md` 要求"登记数量 ≥ 客观算出的 violation 数"而不是"声明修复就放行"的思路是同一类修正。

## W1'（WARNING）：护栏 1 的可判定化范围遗漏 WORKFLOW.md

4.3 节"可判定化方向"提出为护栏 1 增加机械检查：扫描 `dispatch-protocol.md`/`state-machine.md`/`rules/*.yaml` 中的平台名黑名单。但本设计笔记开头"相关文档"列表把 `agate/WORKFLOW.md` 列为权威规则源之一，且 v1 评审已经事实核验过 `WORKFLOW.md:143-148`「已知适用环境」表含平台名。

推演：

```text
护栏1目标：语义锚点文件不得出现平台名
护栏2范围：platform-notes.md / SETUP.md → 整文件视为"如何实现"（豁免）
未回答：WORKFLOW.md 的"已知适用环境"表算语义还是实现？
  - 若算语义 → 该表含平台名，违反护栏1，且未被护栏2豁免，是一个未被本次修订覆盖的既有违规
  - 若算实现 → 护栏2的豁免清单需要补上 WORKFLOW.md，否则将来做"语义锚点文件禁含平台名"的 CI 扫描时，
    扫描脚本的文件清单本身可能与设计笔记开头列出的"权威规则源"清单不一致
```

无论哪种情况，这都是一个本版本没有闭合的边界，会在未来落地"可判定化方向"（写 `check-protocol-consistency.py` 扫描逻辑）时变成一个需要重新决策的分歧点。

可选修正：在护栏 2 的豁免清单里明确列出 `WORKFLOW.md`「已知适用环境」表的归属（建议：与 `platform-notes.md` 同类，整表视为"如何实现"，因为它描述的是"这份文档在哪些平台验证过"而非编排语义本身）；或者在正文里显式排除，避免遗留一个未分类的边界情况。

## W2'（WARNING）：护栏机制仍是"评审时人工检查"，机械化仍是未来时

4.3 节末尾的"可判定化方向"写道"三护栏目前是文档写作纪律，可在 `check-protocol-consistency.py` 增加……检查……把护栏 1 从'评审时检查'升级为'CI 硬校验'"——这句话本身措辞诚实，承认了当前状态。但把它和文档反复援引的"exit code 才是门槛"（BDD-9 哲学红线，4.2 节据此把 gate 判定建模为三态 exit code）放在一起看，存在一个未被文档本身指出的张力：

```text
文档核心论点（4.2）：自动化三件套（推进决策/判定/状态）都不依赖平台能力，全部落在协议内的脚本+数据文件
文档对自己护栏的处理（4.3）：护栏本身不是脚本+数据文件判定的，是"评审时检查"
→ 用来防止协议被平台污染的机制，恰恰是文档里少数几个还没有被"exit code 化"的环节
```

这不是本版本引入的新问题（v1 评审 W3 已经点出"三护栏均为文档写作纪律……与'exit code 才是门槛'哲学存在张力"），但 v2 的修复方式是**补充可操作判据**（护栏变得更容易被人工评审执行），而不是**把判据本身机械化**——这是"让评审员更容易做对的事"和"让脚本自动做这件事"两种不同强度的修复，v2 选了前者，且文档自己把后者标注为未来方向而非本版承诺。

可选修正：若这条护栏被判定为"协议核心一致性的一部分"（类似 S-1/S-2 结构一致性 gate 的地位），建议在下一版明确给出实现优先级（是随 RM-AG0049 一起做，还是单独排期）；若判定为"暂时可以接受评审时人工把关"，建议在文档里也像 4.2 节对待 exit 2 分支那样，显式承认"protocol-consistency 层面目前也有一个'仍需人工判断'的残留点，不假装消除"，与文档其余部分的诚实风格保持一致。

## 建议

1. **最优先**：修正条目摘要的"独立评审 PASS"标注，使其准确反映"v2 是针对 v1 FAIL 评审的修订版，尚未有独立复审确认"的真实状态；若已有真实的 v2 独立复审，应作为单独文件附上，而不是让摘要标签替代复审证据。
2. 补齐护栏 2 豁免清单，明确 `WORKFLOW.md`「已知适用环境」表的归属（建议归为"如何实现"）。
3. 对护栏机制的机械化（`check-protocol-consistency.py` 平台名黑名单扫描）给出后续排期判断，或至少显式承认这是当前设计的一个"仍靠人工评审"的残留点，与 4.2 节对 exit 2 分支的诚实态度保持一致。
4. 可选：把 4.1 节的平台实现映射表移至 4.2，让语义叙述与实现映射的排版分离更彻底地对齐护栏 3。
5. 核验 `docs/design-notes/README.md` 登记状态（仓库内可直接确认，无需等待下一轮设计修订）。

## 内容质量的整体判断（与"是否通过"分开说明）

需要明确区分两件事：**v2 文档内容本身的修订质量**，与**"独立评审 PASS"这个标签是否站得住脚**。

就前者而言，v2 相对 v1 的修订是扎实的——五模式措辞纠正、资产盘点补全、"100%可程序化"表述收敛为"主线推进+单步回退"、回退语义对齐 `state-machine.md`、exit 三态显式建模、护栏补充可操作判据，这些修改大多能在文档内部找到对应的、有依据的改动，不是同义反复的文字游戏。方向上（领域专用状态机 + 协议内自动化 + 平台降级为执行环境）与已验证过的仓库现状（`check-state-transition.py`、`rules/` 结构化层、`/loop` 三档自动化）契合，延续了此前 RM-AG0046 那次评审所验证的"协议核心机制运转良好"的判断基础。

就后者而言——即条目自称的"独立评审 PASS"——**不成立**，这是本次评审最主要、也是唯一的 BLOCKER 级发现：现有证据只能证明"提交者按 v1 评审意见做了修订"，不能证明"有独立评审者验证过这些修订本身是否正确、完整、没有引入新问题"。而本次审查确实在 v2 里找到了两个 v1 评审没有触及、修订过程中新出现或被延续下来的 WARNING 级问题（护栏范围遗漏 WORKFLOW.md、护栏机械化仍是未来时），这恰好印证了"自评通过"和"独立复核通过"不是同一件事——如果真的有人做过针对 v2 的独立复审，这两点大概率会被提前发现。

## 补充：超出本次评审范围的几点设计想法

以下内容不是对文档"是否属实/是否自洽"的评审结论，而是站在已核实的协议现状（`check-gate.py` exit 三态契约、`check-state-transition.py` 机械拦截、`agate-retreat-to.py` 回退侧 CLI、known-failures/known-violations 三重门槛的既有经验）之上，对这份设计笔记提出的几点**补充性想法**，供 RM-AG0049 立项讨论时参考，不构成本次独立评审 PASS/FAIL 结论的一部分。

### 想法 1：exit 2 的"下一动作"字段，可以直接照抄 known-violations 三重门槛刚验证过的模式，而不是重新设计

v2 第 7 节给 exit 2 留了一个待定的"下一动作"字段（如"P5 exit 2 → 主 Agent 跑 gate_commands.P5"），但这个字段目前还只是占位描述，没有给出统一的数据结构。这里有一个现成的参照系：RM-AG0046 从 v1 到 v3 踩过的坑，核心教训是"复刻一个机制的算法容易，复刻它背后的语义约束容易漏"（known-failures vs known-violations 那次道德语义颠倒的教训）。exit 2 的"下一动作"字段如果只是一个自由文本描述（"主 Agent 跑 gate_commands.P5"），本质上又是一次"self-authored"——是否真的跑了 gate_commands.P5、跑完之后算不算通过，仍然是主 Agent 自己说了算，状态机查表查到 exit 2 之后立刻退回到"信任模型”。

更值得考虑的设计是：把 exit 2 的"下一动作"本身也建模成一个**可机械复核的子状态**，而不是一句自然语言描述——比如要求"下一动作"执行完之后必须产生一个新的、可被 `check-state-transition.py` 读取的落盘产物（哪怕只是一个"exit2-resolution.md"或者一条 `.state.yaml` 字段，记录"exit 2 是在什么时间、依据什么客观依据被谁解决的"），这样至少能让 P6.5 judge 或 provenance 审计事后核查"这次 exit 2 分支到底有没有被真的处理，还是被悄悄跳过了"。这不是要消灭 exit 2 残留的模型依赖（文档已经诚实承认这点不该假装消除），而是让这段"必须信任模型"的区间，至少留下审计痕迹——和协议现有的"判定权可以留给模型，但过程必须留痕"这条一贯思路一致。

### 想法 2：状态机 CLI 和 /loop 档位 C 的关系，建议不是"二选一"而是"CLI 是档位 C 的可观测层"

v2 第 5 节已经提出这个问题（"状态机 CLI 与 /loop 档位 C 重叠"），并倾向于"机械替身"这个定位。这里有一个补充角度：档位 C 目前"自动跑 P1-P8、硬中断点必停"的执行者是主 Agent 本身——也就是说，档位 C 的"自动"，实际上是**同一个模型在多轮里反复对自己说"该往下走了"**，这本质上和"编排决策仍是模型"这条张力（文档 1.2 节）是同一个问题的另一种表现形式，只是发生在更宏观的多阶段循环层面，而不是单次 phase 推进层面。

如果状态机 CLI 落地后，档位 C 的"自动推进"可以被要求走 CLI（`agate next`）而不是主 Agent 自己判断"该继续了"，那么档位 C 就从"模型自己决定要不要继续循环"变成"模型只负责执行内容，循环节奏由脚本控制"——这是一个比"CLI 是档位 C 的机械替身"更强的定位：**CLI 不只是替代档位 C 的实现，而是消除档位 C 里唯一一处目前仍然完全依赖模型自律的环节**（"知道什么时候该停、什么时候该继续"）。这个角度或许值得在 RM-AG0049 落地时补一条 BDD：验证"档位 C 全程使用 `agate next` 推进，主 Agent 从未自行判断是否进入下一 phase"，把这一条也变成可核验的验收标准，而不只是架构描述。

### 想法 3：转移表落地后，建议同时补一条"转移表与 state-machine.md 权威源的双向一致性 gate"

文档已经决定"回退目标照抄 state-machine.md"（第 7 节），这个决定是对的，但目前的落地路径（第 6 节 Phase 1）没有提到**怎么保证 `phases.yaml` 里新增的 next/retreat 字段和 `state-machine.md` 的文字描述不会日后逐渐漂移**。协议里已经有一个现成的先例可以照抄——`rules/state-transitions.md` 的 S-1/S-2 双向一致性 gate（v2 第 5 节资产表已经提到这个机制存在），职责就是防止"结构化数据面"和"人类可读的权威源"这两份东西各自被改动后互相脱节。

建议 Phase 1 落地时，`phases.yaml` 新增的 next/retreat 字段直接纳入现有 S-1/S-2 一致性 gate 的检查范围（而不是新开一个独立的一致性检查），这样"转移表" 从诞生的第一天起就有机械化的防漂移保障，而不是等到某次真实任务里"CLI 推进结果和 state-machine.md 描述对不上"才发现两者已经脱节——这类问题一旦发生，排查成本会比现在多花一点设计成本去预防高得多，RM-AG0046 那次 B1（挂载阶段错位导致检测器完全不生效）就是同一类"设计时假设成立、后来悄悄不成立"的教训。

### 想法 4：护栏 1 的"平台名黑名单扫描"，建议扫描对象从"文件名单"改为"数据面 vs 叙述面"的结构性判据

W1'/W2' 已经指出护栏 1 目前的扫描范围（`dispatch-protocol.md`/`state-machine.md`/`rules/*.yaml`）可能遗漏 `WORKFLOW.md`，而且不断有类似 `WORKFLOW.md` 这样"既是流程权威源、又难免要提一下'这条规则在哪些平台验证过'"的文档冒出来，靠维护一份不断增补的文件名单本身就是一种脆弱的护栏设计——新增一份权威文档时，很容易忘记把它加进扫描名单。

更结构性的判据是文档 4.3 护栏 2 其实已经隐约触及但没有明说的一条原则：**凡是 `rules/*.yaml` 这类机器可读数据面，禁止出现平台名；凡是 markdown 叙述文档，允许出现平台名，但仅限于附带"如何实现"标记的小节/表格**（比如统一要求这类小节前面加一个固定的标记行，如 `> 实现注记：`），护栏检查脚本就不需要维护一份文件白名单/黑名单，而是扫描"markdown 文档里所有不带`实现注记`标记、但含平台名的段落"——这样不管未来新增多少份权威文档，只要作者遵守"含平台名的内容必须挂实现注记"这条统一格式约定，护栏就自动覆盖，不需要每次新增文档时再去维护扫描名单。这个想法的代价是需要对现有文档（至少 `WORKFLOW.md`、`dsh-integration.md`）做一次格式补标，但换来的是护栏本身不再随文档数量增长而失效。
