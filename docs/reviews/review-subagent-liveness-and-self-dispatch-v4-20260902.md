# v4 增量评审：§3.4.1 心跳检测范围分层分析

审查前核验：`docs/design-notes/design-subagent-liveness-and-self-dispatch.md` 定稿 **231 行**，`docs/design-notes/README.md` 登记已同步更新为 v4 描述。本轮为增量评审，不复查 v3-fix 已确认闭合的 B1/B2/R1/R2/W1（心跳双路径设计、评审链证据问题），只审新增内容。

## 核验结果

| 检查点 | 结果 |
|---|---|
| 三分类（进程/会话级、单次系统调用阻塞、逻辑空转）是否穷尽了"卡死"的常见成因，有无遗漏第四类 | 基本穷尽主要场景；未覆盖"平台服务端限流/排队"这类不属于 subagent 自身故障、但外部表现也是"长时间无响应"的情况——不过这类情况本质上是"派发尚未真正开始执行"，不是"subagent 已运行后卡死"，与本节讨论范围（subagent 运行中卡死）不同类，不判定为遗漏 |
| "CPU 打满导致心跳与被阻塞调用一起变得不新鲜"被表述为"加分项"，是否夸大了心跳机制在此场景下的确定性 | 表述已加了限定语"依赖…前提"，且明确说是"能检测出资源层面整体阻塞"而非"总能检测"，未过度断言，用词克制，可接受 |
| "逻辑空转是心跳机制的天然盲区，不属于本设计范围"是否与 §2 非目标一致，有无自相矛盾 | 一致。§2 非目标已声明"不提供心跳以外的进度语义解释能力"，本节的表述是对该非目标的具体化解释，不是新增排除项，无矛盾 |
| 诚实边界声明的补充措辞（"仅限于进程级/会话级卡死…不覆盖逻辑空转"）是否准确对应表格结论，有无表述漂移 | 准确对应，未引入表格之外的新断言 |
| 新增内容是否影响 §3.4 第 2、3 条已有表述的正确性（是否需要联动修改）| 不需要——第 2、3 条讲的是"检查时机"与"产生者"，§3.4.1 讲的是"检测范围边界"，二者是互补关系，第 2/3 条未做任何与本节矛盾的确定性断言，无需改动 |

未发现 BLOCKER 或 WARNING。轻微措辞建议（NIT，不阻断）：表格第二行"CPU 被打满导致所有进程调度不到"这一表述可以更精确为"CPU 或其他共享资源（如 cgroup 限额）被打满"，因为容器化环境下更常见的是 cgroup 限流而非物理 CPU 打满，但这不影响结论正确性，可在下次改动时顺手处理。

## 结论

**PASS**。§3.4.1 新增内容准确回答了"心跳会不会跟着 subagent 一起卡死"这一问题：进程/会话级卡死会让心跳一起停止（可检测，是本设计的主要覆盖场景），逻辑空转不会让心跳停止（不可检测，是心跳机制的天然盲区，已诚实标注不在本设计范围）。表述与全文其余部分（§2 非目标、§3.4 既有条款）一致，无自相矛盾，无需进一步修改即可作为定稿内容。
