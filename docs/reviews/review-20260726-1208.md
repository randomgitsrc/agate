## 三、非阻塞建议

`check-gate.sh` 里"预存失败必须登记"的判定（第 186 行）只检查 `known-failures.md` **是否存在**，不检查内容。PG.9 的测试用例甚至专门确认了"只有 frontmatter 的空文件也会 exit 2 放行"是当前的预期行为。

对比这个机制想解决的 T068 问题（主 Agent 一句"非本任务相关"就把 63 个预存失败带过、未登记未排查）——一个仅有 frontmatter 的空 `known-failures.md` 在"有没有登记"这个意义上和"完全不提"相比，信息量并没有实质增加，主 Agent 仍然可以不写明具体是哪些失败、成本几乎为零地通过 gate。这不是本 PR 引入的新洞（此前甚至连"文件存在"这一步都不检查，所以严格来说是净改善），但如果目标是彻底堵上 T068 同类问题，这里还留了一个字面意义上"文件存在但没写什么"的空子。

建议：后续可以加一条低成本的机械检查——`known-failures.md` 里登记的失败 id 数量 ≥ `STILL_FAILING` 的数量（或做一次简单的子集匹配），而不只是判断文件存在性。不建议现在为此阻塞合并，因为：(1) 这是相对于现状的净改善而非退步；(2) 计划文档 §0.2 明确把"预存失败要不要顺手修"这个语义判断留给主 Agent/人，登记内容的语义完整性本身也接近这一类判断，不一定适合在这个粒度上机械化；(3) 现有 12 个 PG 用例已经把这个已知边界诚实地测出来了，不是被掩盖的问题。
