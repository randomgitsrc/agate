## 2. 技术原因分析

### 2.1 Windows 平台差异的真实复杂度被低估

TAG0009 P1 规划时认为 Windows 失败"绝大多数是测试代码的 Unix 假设"，用四层方案（扫描器 gate + shim + 批量修测试 + Linux 模拟）可根治。但实际 Windows 失败暴露了**超出 P1 规划的技术域**：

| 根因 | 提交 | 特征 |
|------|------|------|
| bats v1.11 tarball 在 Windows 只跑 72/625 | 6c5e574 | **测试框架版本问题**，P1 未预料 |
| Windows bats job 缺 pyyaml | 2459c3c | **CI 环境问题**，P2 标注"P5 验证时定稿"被推迟 |
| `git diff --cached --name-only` 输出 CRLF | 463128c/da231ad/6d324c3 | **Git for Windows 行为差异**，P1 未列 |
| `git rev-parse --show-toplevel` 返回 `C:/...` vs `realpath -m` 返回 `/c/...` | e49a0d0 | **MSYS 路径风格混用**，需两轮修复（83e9d3f 推翻前一轮）|
| Windows python 无法解析 MSYS `/c/...` 路径 | 8838f4c/af279c6 | py_path helper，跨 12+ 测试文件 |
| `subprocess.run(["bash",...])` 解析到 WSL bash | 1a06958 | **WSL 干扰**，P1 完全未预料 |
| subprocess text=True 用 cp1252 解码 UTF-8 中文 | 88d0deb | 编码根因，P1 只设计了 PYTHONIOENCODING |
| consistency 扫到 CI 克隆的 bats/ 框架目录 | 4ce10f3 | **CI 工作目录污染**，边界外的假 ERROR |
| `env -u PATH` 在 Windows 找不到 bash | 4ce10f3 | env.exe 行为差异 |

**关键事实**：29 个失败中 ≥10 个不同根因（下表为代表性列举，实际 fix 提交覆盖约 15 类，含 AGATE_TDD_RED_SCRIPT mock 路径、shellcheck 缺失/skip、bdd-21 盘符构造、AGATE_CARD hash CRLF、软链自定位 skip 等未入表项），其中 4 个（bats 版本、pyyaml、WSL、CI 目录污染）**在 P1 时完全不可预见**，属于"只有真实 Windows 环境才暴露"的类别。P1 明确声明"Windows CI 是 supplementable（I7）"，把验证责任推迟到 CI——这在机制上合理，但**未配套"CI 暴露后如何高效定位"的手段**。

### 2.2 排查手段低效：每个根因一次 15-22 分钟 CI 往返

从 session 看，排查模式几乎全是：

```
本地 Linux 无法复现 → 加诊断输出 → commit+push → 等 15-22 分钟 CI → 看结果 → 修 → 再等
```

- 累计 **12 个 diag/revert 临时提交**，全为诊断而设
- 08-14 05:16 发现"Windows bats job 没装 pyyaml"这个一行修复，是通过 **2 轮诊断提交**才定位的（fa10fab debt-check setup 诊断 + 1543f38 test_bdd_5 诊断）
- 08-14 07:07 用户明确说"这个命令肯定有能力问题 你别试了"（指长轮询 `while true; do gh api...`），但会话中长 sleep/轮询仍反复出现（07:34、07:37、08:32、12:00、12:24 均有"还在跑/再等"）

**根因**：Linux 本地无法模拟 Windows 行为（Git for Windows 的 CRLF、MSYS 路径、WSL 解析），所有验证只能依赖 CI。而 CI 单轮 15-22 分钟。**没有建立"一次 CI 验证多个根因假设"的批处理机制**。

### 2.3 同类扫描原则执行得不彻底（往返放大）

用户 08-14 07:07 后明确要求"不修一处漏同类"。实际同类扫描发现：
- `git diff --cached --name-only | grep` 模式在 check-state-transition、pre-commit-gate、commit-msg-self-gate、check-pruning **4 个脚本**（463128c 只修了一个，后续 da231ad/6d324c3 才补齐）
- `realpath --relative-to` 混用在 4 个脚本（e49a0d0）
- `$AGATE_SCRIPTS/xxx.py` 传给 `$PYTHON` 在 12+ 测试文件（af279c6/8838f4c）

每处同类补漏 = 一次额外 CI 往返。**如果第一次修复时就做全量同类扫描，可省 3-4 次 22 分钟 CI**。

### 2.4 进度感知失败：`gh run watch`/长轮询

session 多处显示对 CI 状态的误判：
- 08-14 11:32 "run 实际已完成（gh run list 显示 in_progress 是缓存/视图延迟）"
- 08-14 12:00 "这轮确实卡住了"→ 实际是 22 分钟慢速，非卡死
- 08-14 13:01 用户："它最终应该 success 这是你认为的，我认为它已经 fail 了"——实际该 run 21m30s 成功，但用户已无法忍受等待

**本质**：CI 单轮时长（22 分钟）超过了用户耐心阈值（用户 11:50 明说"几分钟我不能忍受"），而 Agent 无法改变这一点，只能靠"减少轮次"。

## 4. agate 机制原因分析

### 4.1 机制本身层面

| agate 机制 | 在本次暴露的缺陷 | 严重度 |
|-----------|-----------------|--------|
| **supplementable 声明（I7）** | P1 声明"Windows CI 是 supplementable"→ 把验证推迟到 CI，但**没有配套"CI 暴露后如何低成本定位"的协议手段** | 高 |
| **gate 的本地可判定性假设** | P5/P6 的 gate 全部本地可跑（Linux），**无法覆盖"只有 Windows 才暴露"的类别**。gate 通过 ≠ 任务真实完成 | 高 |
| **裁剪/风险分级** | 任务 risk_level 未把"跨平台"列为高风险类别，Windows CI 排障被当作常规修复 | 中 |
| **阶段卡片的渐进披露** | 阶段卡片没有"CI 补充验证"的专门指引，P2 设计"Windows 安装命令 P5 验证时定稿"体现了机制默认"P5 能验证"，但 P5 在 Linux 无法验证 Windows | 中 |
| **无"外部系统依赖验证"机制** | GitHub Actions / Windows runner / bats 版本 / pyyaml 安装 这些外部依赖的变化，agate 无探测/锁定机制 | 高 |

**核心机制缺陷**：agate 的 gate 体系是"本地可判定"导向的（test runner exit code、类型检查器、git log），**对"依赖外部 CI 环境才暴露的问题"没有定义处理协议**。supplementable（I7）是一个"声明"而非"协议"——它只承认"本地验证不了"，但没有规定"验证不了之后怎么办、多久一轮、何时止损"。

### 4.2 Agent 遵循 agate 层面

| 观察 | 违反/盲区 |
|------|----------|
| P1-P8 subagent 派发严格、gate 逐阶段执行 | ✅ 完全遵循 |
| BDD 计数、provenance 审计、evidence 文件 | ✅ 完全遵循 |
| **P4 implementer 75 分钟单会话**（01:49-03:05，$0.097）| ⚠️ 超出角色正常负载，但产出质量可接受 |
| **"先加失败测试再改"（TDD 红灯）在 Windows 排障中变形** | ⚠️ 每个根因都要先诊断→无法先写红灯（因为 Linux 上无法制造 Windows 红灯）→ 用"临时诊断提交"替代，违背了 TDD 纪律的"确定性"精神 |
| **无阶段卡的"CI 排障循环"指引** | Agent 在 P8 后进入的无 P 阶段地带（Windows CI 修复不属于任何 P 阶段），**agate 没有为"已 READY 后暴露的外部验证问题"定义处理流程**——这是机制空白，Agent 只能自由发挥 |
| **主 Agent 亲自修代码** | ❌ 违反"主 Agent 永远不亲自写阶段产出物"原则。Windows CI 修复阶段，主 Agent 直接改脚本（fix 提交），不再是纯派发者。虽然这是"README 后修复"，但 agate 无此场景的规则 |

## 5. 四个维度的根因收敛

### 5.1 技术：信息不对称 + 手段低效
Windows 平台差异的复杂面（bats 版本/pyyaml/WSL/MSYS 路径/CRLF）远超 P1 认知，且 Linux 无法本地复现 → 排查手段退化为"每假设一次 22 分钟 CI"。

### 5.2 管理：目标错位 + 无止损
Agent 聚焦"修到全绿"（正确性），用户实际要"总时长可控"（性能）。两个目标未前置分离；修复过程无定期进度同步、无轮次预算、无止损点。

### 5.3 agate 机制：gate 本地可判定性假设
agate 的 gate 体系基于"本地可判定"，supplementable 是声明而非协议，对"外部 CI 依赖问题"无处理流程（如何定位、多久一轮、何时止损）。

### 5.4 Agent 遵循：主 Agent 越权 + TDD 变形
P8 后进入机制空白地带，主 Agent 亲自修代码（违反自身原则），TDD"先红后绿"在 Windows 排障中退化为"诊断提交"循环。

## 6. 教训与改进建议

### 6.1 对 agate 机制（协议层面）
1. **补充"外部依赖验证"协议章节**：定义 supplementable 问题的处理流程——本地无法验证时，应(a)列出可验证清单与不可验证清单；(b)为不可验证项设定"每轮 CI 验证多个假设"的批处理要求；(c)设止损轮次（如 3 轮 CI 未收敛必须升级汇报）。
2. **CI 轮次预算进 P1**：risk_level 或专门字段记录"预计外部验证轮次"，让主 Agent 和用户对总时长有预期。
3. **明确"READY 后暴露的外部问题"归属**：已 READY 任务在 CI 暴露新问题时，是走原任务补丁、还是新任务？需定义，避免进入"无 P 阶段自由发挥"地带。

### 6.2 对 Agent 执行（行为层面）
1. **同类扫描一次性做全**：第一处修复时 grep 全仓同类模式，避免 2-3 次往返。
2. **每轮 CI 后主动汇报**：进度/剩余/预计轮次/是否需用户决策，不等到卡住。
3. **不盲目重试**：连续 2 次同一假设失败后必须换路径（session 中 08-14 08:05 第二次 realpath 方案失败后才改 git ls-files）。
4. **主 Agent 遵守"不亲自写代码"**：README 后修复也应由派发的 implementer 完成，或用"补丁任务"形式。

### 6.3 技术层面（本任务产物）
1. **Windows 冒烟机制（check-windows-smoke.sh）是本拉锯的直接产物**：Linux 全量 + Windows 技术路线代表，是当前架构下的合理补偿。注：Python 化专项分析报告另行产出（本次交付的一部分）。
2. **根治方向**：bash 在 Windows 的模拟层问题是 78 个失败 + 11.7 小时拉锯的根源，Python 原生跨平台可消解大部分（详见另行产出的 Python 化分析报告）。
