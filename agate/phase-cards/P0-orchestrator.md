# P0 — 任务启动

> P0 不派 subagent（主 Agent 亲自执行）。结构与其他卡片不同。
>
> 当前阶段：P0

## 做什么

P0 是立项阶段。主 Agent 自己写完 P0-brief.md，不派 subagent。

## P0-brief.md 四字段

```yaml
task: "一句话描述任务（工程视角）"
known_risks:
  - "涉及数据 schema 变更"
  - "跨越多个改动端"
executor_env:
  platform: "opencode"
  has_task_tool: true
  has_local_runtime: true
  network: "full"
env_constraints:
  debug_env: "项目的测试/调试环境命令或路径"
```

任一字段为空占位符 → 补完再推进 P1。四字段是 agate 要求的最小集，项目可按需扩展。

## 同类/影响面预判（强制，写在 known_risks 里）

填 `known_risks` 时不止列"这个改动有什么风险"，还要先做一次**同类/影响面预判**——问题很少只有一个实例，只修被报告的那一处是 agate 反复踩到的坑。

预判三问（结论写进 `known_risks`，哪怕结论是"已确认只此一处"）：

1. **同类实例**：这个问题/改动模式在仓库里还有没有别的实例？用 grep/rg 扫一遍关键符号（函数名、字段名、配置键、文案），把命中数量与文件清单记下来
2. **上下游消费方**：被改动的对象（字段/接口/文件/协议节）有哪些消费方？改了之后谁会跟着变
3. **同类未来实例**：这次是"修一处"还是"立一条规则"？若同类问题还会新增，`known_risks` 要注明需要防回归的拦截手段（测试 / gate 脚本 / 文档约定）

写法示例：

```yaml
known_risks:
  - "同类/影响面预判：grep `verification_env` 全仓命中 4 处（dispatch-protocol.md / verifier.md / P5 卡 / P6 卡），本次须同批处理，不能只改 1 处"
  - "同类/影响面预判：新增字段无运行时消费方，靠文档约定 + grep 断言测试兜底"
```

预判是 P0 的**粗粒度**版本，只要求给出量级和清单；P1 的「同类扫描」、P2 的「影响面梳理」在此基础上逐级细化（三处措辞不同但同源，见 P1/P2 卡片对应节）。

## P0-brief 时效性自检（漂移判据）

P0-brief 写完不等于永久有效。**立项时间与实际启动/恢复时间存在间隔**（跨会话恢复、任务被搁置后重启、从 PAUSED 恢复）时，推进 P1 前必须对照下面的判据做一次时效性校验，判断 P0-brief 是否已漂移。

**严重漂移**（命中任一条 → 回 P0 重新立项 / 重做可行性分析，不允许带着失效前提推进）：

1. `task` 字段描述的目标方案本身不再成立（所需修改的技术路线 / 架构已变化）
2. `executor_env` 声明的平台 / 运行时前提不再成立（声明的 CI 环境或工具链已下线、大版本不兼容）
3. `known_risks` 中被判定为"已解决前提"的条目实际仍未解决；或反之已被其他任务解决，导致本任务范围重叠 / 失效

**轻微漂移**（不命中以上任一条 → 更新 P0-brief 对应字段 + 标注 `[P0_STALE]` 后继续，不阻塞）：

4. 局部细节变化（文件路径、依赖版本号、单个工具调用方式）不影响任务方案选择
5. `env_constraints` 的具体值需刷新（如 `debug_env` 端口变化）但环境类型未变

**判定流程**：对照 1-3 逐条排查 → 命中任一条 = 严重（回 P0）；全部不命中 = 轻微（更新字段 + `[P0_STALE]` 标注 + 继续 P1）。

⚠️ 不要用"距立项过了几天"当判据——时间与漂移程度不相关：隔 2 天技术路线切换是严重漂移，搁置 60 天但项目没变只是轻微。判据看的是**前提是否还成立**，不是过了多久。

标注格式与 P1 阶段的处理规则（阻塞 / 记录二选一）见 P1 卡片「P0-brief 时效性质疑」节。

## 环境自检

启动任务前必须确认环境可用（不确认不得推进 P1）：
- debug 环境可访问（curl health check / 启动服务）
- 测试框架可用（项目使用的测试框架，如 pytest/vitest/go test/cargo test --version）
- 浏览器自动化可用（playwright --version，UI 任务时）

## 任务粒度

若写不出一句话任务描述 → 任务太大，必须拆分为多个任务。不允许用模糊描述强行通过。

## 推进条件（全部满足才推进）

- [ ] P0-brief.md 四字段齐全（无空占位符）
- [ ] `known_risks` 含「同类/影响面预判」结论（哪怕结论是"已确认只此一处"）
- [ ] **P0-brief 时效性自检已执行**（见「P0-brief 时效性自检（漂移判据）」）：严重漂移 → 回 P0 重新立项；轻微漂移 → 已更新对应字段并标 `[P0_STALE]`；无间隔或无漂移 → 记录"已核对，无漂移"
- [ ] 环境自检已执行（debug 环境 / 测试框架 / UI 任务的浏览器自动化）
- [ ] {AGATE_WORKSPACE}/tasks/active-tasks.md 已写入新任务行

推进后 → 读 P1 卡片

## loop 模式

若使用 `/loop` 自动编排：P0 完成后主 Agent 按顺序自动推进 P1→P8，遇 PAUSED 或异常时停下。

## 任务类型提示

**hardening / refactor 类任务**：P0-brief 建议包含代码审计结果（现有代码的问题清单），作为 P1 需求的输入。P0 卡片不强制要求审计（非门槛），但跳过审计可能导致 P1 需求不完整、P2 设计基于错误假设。

## P0-brief 质量自检（源自 office-hours 六问）

写完 P0-brief 后对照自检（非门槛，但跳过可能导致 P1 需求不完整）：
1. 需求真实性：有没有人真的需要这个（不是假设性需求）
2. 现状：用户现在怎么解决这个问题
3. 绝望的具体性：最痛的那个人是谁
4. 最窄切入点：最小可交付版本是什么
5. 亲眼观察：有没有看过实际使用场景
6. 未来契合：这个方向长期是否成立

## 下游影响

P0-brief 的 env_constraints / known_risks / executor_env 会在 P1-P8 每个阶段派发 subagent 时注入。写清楚能让每个 subagent 知道项目约束。
